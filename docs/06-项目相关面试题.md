### 📝 简历上的完整项目经验（Java版）

**项目名称：项目交付管理系统 - PMO 智能知识助手**

**技术栈：** Java 17, Spring Boot, LangChain4j (或 Spring AI), Milvus, Redis, Apache Tika, RabbitMQ, Spring Data JPA

**项目简介：**
面向 IT 外包公司交付经理打造的**项目交付过程智能辅助工具**。针对多项目并行管理时文档查阅慢、交接成本高的痛点，系统支持以“项目”为维度创建独立知识库，沉淀 PRD、周报、会议纪要、风险日志等交付资产。基于 RAG 技术实现智能问答，帮助交付经理快速追溯需求变更、盘点项目风险，大幅提升日常交付与交接效率。

**责任描述：**
1. **知识库架构与文档解析分块：** 设计以“项目”为核心维度的知识库架构。基于 **Apache Tika** 和 **Apache POI** 构建文档解析流水线，针对项目计划（WBS表格）、会议纪要（Action Item）等混合结构，自定义分块（Chunking）策略，将复杂表格转化为 Markdown 格式，保障业务语义的完整性。
2. **RAG 检索链路优化：** 基于 **LangChain4j** 构建“向量检索 + BM25关键字”的混合检索链路，并引入 Rerank 模型进行二次重排序；优化交付场景的 Prompt 模板，实现长篇 PRD 的精准问答与项目周报的自动摘要提取。
3. **多轮对话与原文溯源：** 利用 **Spring Data Redis** 管理对话上下文，结合 LLM 进行 Query Rewrite（查询重写）以解决多轮对话中的指代不清问题；实现答案的原文溯源功能，前端通过锚点高亮展示引用的原始文档段落。
4. **异步入库与 Metadata 构建：** 设计基于 **RabbitMQ** 的异步文档入库流水线，避免大文件解析阻塞主线程。在入库时自动提取并注入多维 Metadata（项目ID、文档类型、所属阶段），为后续的检索过滤提供底层数据支撑。
5. **项目级权限隔离：** 在 **Milvus Java SDK** 检索阶段，通过动态拼接标量过滤表达式（Expr）强制执行元数据过滤，确保交付经理仅能检索自身负责的项目数据，防止跨项目敏感信息泄露，满足外包合规要求。

### 🔥 核心面试问题与技术细节扩展（Java 视角）

#### 一、 文档解析与分块 (Java 特有痛点)

**1. Java 解析 Word/PDF 有什么坑？大文件导致 OOM 怎么解决？**
*   **面试官意图**：考察 Java 处理非结构化数据的真实经验和 JVM 内存管理。
*   **参考回答**：
    *   **解析工具**：我们底层封装了 **Apache Tika** 作为统一入口，它会自动路由到 **Apache POI** (处理 Word/Excel) 和 **PDFBox** (处理 PDF)。
    *   **OOM 痛点**：以前用 `XWPFDocument` (POI) 直接 `new` 一个几百兆的 Word 文件，会把整个 DOM 树加载到内存，极易引发老年代 OOM。
    *   **解决策略**：
        1.  **流式读取**：对于大文件，改用 POI 的 `SXSSFWorkbook` (Excel) 或基于 SAX 的事件驱动解析 (Word)，不一次性加载全量 DOM。
        2.  **PDFBox 内存映射**：使用 `PDFBox` 的 `MemoryUsageSetting`，将临时数据交换到磁盘（Scratch File），而不是全放在 JVM 堆内存中。
        3.  **异步与隔离**：文档解析是 CPU 和内存密集型操作，我们通过 **RabbitMQ** 将解析任务异步化，并给解析 Worker 分配独立的线程池和更大的 JVM 堆内存（如 `-Xmx2g`），防止解析大文件时拖垮核心的 Web 接口。

**2. 针对 WBS 表格，你的“自定义分块策略”在 Java 里怎么落地的？**
*   **参考回答**：
    *   传统的 `RecursiveCharacterTextSplitter` 会把表格切碎。我们在 Java 里写了一个自定义的 `DocumentTransformer`。
    *   当 Tika/POI 解析出 `Table` 节点时，我们不走普通的文本切分。而是遍历表格的行（Row）和列（Cell），提取表头（Header）。
    *   **核心逻辑**：将每一行数据与表头拼接。例如表头是 `[任务, 负责人, 状态]`，数据行是 `[登录开发, 张三, 完成]`，我们在 Java 里将其拼接成字符串：`"任务:登录开发 | 负责人:张三 | 状态:完成"`。
    *   这样生成的每一个 Chunk 都自带完整的上下文，送入 Embedding 模型时语义非常清晰。

#### 二、 RAG 检索链路优化 (LangChain4j / Spring AI)

**1. 在 Java 生态里，你是怎么做混合检索（向量+BM25）和 RRF 融合的？**
*   **参考回答**：
    *   我们使用了 **LangChain4j** 框架。它提供了 `HybridSearch` 的概念，但在实际落地中，为了更精细的控制，我们手动实现了 RRF（倒数秩融合）。
    *   **实现细节**：
        1.  利用 Java 的 `CompletableFuture` **并发**发起两个请求：一个是调用 Milvus 做向量检索（Top 50），另一个是调用 Elasticsearch (或 Milvus 的全文检索) 做 BM25 关键字检索（Top 50）。
        2.  拿到两个 `List<Document>` 后，在 Java 内存中执行 RRF 算法：遍历两个列表，根据文档的 `doc_id` 计算 RRF 得分 `1 / (k + rank)`。
        3.  使用 Java 8 的 Stream API 对结果进行分组、求和、降序排序，截取 Top 10。
    *   **代码感**：`Map<String, Double> rrfScores = new HashMap<>(); ... Collections.sort(...)`

**2. Rerank（重排序）模型在 Java 里怎么集成？**
*   **参考回答**：
    *   由于 Cross-Encoder 类的 Rerank 模型（如 bge-reranker）用 Python 跑最方便，我们在 Java 端通常有两种做法：
        1.  **调用外部 API**：如果公司采购了阿里云/百度的 API，直接用 `OkHttpClient` 或 `RestTemplate` 封装 HTTP 请求调用。
        2.  **本地部署 Python 微服务**：用 FastAPI 写一个极简的 Rerank 服务（只暴露一个 `/rerank` 接口），Java 端通过 HTTP/gRPC 调用它。
    *   在 LangChain4j 中，可以实现自定义的 `ContentRetriever` 或 `ScoredDocumentTransformer` 接口，在粗排结果返回后，拦截并调用 Rerank 服务进行重排。

#### 三、 多轮对话与上下文管理

**1. 多轮对话中的指代词（如“那它的风险呢”），在 Java 里怎么处理？**
*   **参考回答**：
    *   这是经典的 **Query Rewrite（查询重写）** 问题。
    *   我们在 Spring Boot 中定义了一个 `QueryRewriteService`。在用户提问进入 RAG 检索前，先拦截。
    *   从 Redis 中获取最近 3 轮的历史对话（使用 `Spring Data Redis` 的 `ListOperations`）。
    *   拼接一个 Prompt 发给 LLM：“*根据历史对话，将最新问题补全为独立完整的查询词。历史：[...] 最新：那它的风险呢？*”
    *   LLM 返回“*A项目延期的风险有哪些*”后，我们再拿这个重写后的 Query 去 Milvus 检索。

**2. Redis 存上下文，如果 Token 超了怎么办？**
*   **参考回答**：
    *   不能无脑把 Redis 里的历史全塞给 LLM。
    *   我们在 Java 里实现了一个**滑动窗口 + 摘要降级**策略。
    *   如果 `List` 的长度超过 6 条（3轮），我们会触发一个 `@Async` 异步任务，把这 6 条发给 LLM 生成一段 200 字的“对话摘要”。
    *   然后把 Redis 里的这 6 条删掉，替换成一条 Role 为 `System` 的摘要消息。这样既保留了长期记忆，又控制了 Token 成本。

#### 四、 项目级权限隔离（🔥 核心：Milvus Java SDK 底层实现）

**1. 权限隔离在 Milvus Java SDK 底层的查询语句是怎么写的？（必问细节）**
*   **面试官意图**：看你到底是调包侠，还是真的看过 SDK 源码和 API 文档。
*   **技术细节与代码示例**：
    在 Milvus Java SDK (2.x 版本) 中，权限隔离是通过 `SearchReq` 中的 `filter` (标量过滤表达式) 来实现的。

    ```java
    import io.milvus.v2.service.vector.request.SearchReq;
    import io.milvus.v2.service.vector.request.data.FloatVec;
    import io.milvus.v2.common.IndexParam;
    import java.util.*;

    // 假设当前登录的交付经理ID是 "DM-0042"，正在查看项目 "PRJ-001"
    String currentProjectId = "PRJ-001";
    String currentUserId = "DM-0042";

    // 1. 动态拼接 Filter 表达式 (类似 SQL 的 WHERE)
    // 核心：限制 project_id，并且限制 owner_id 或者是公共文档
    String filterExpr = String.format(
        "project_id == '%s' and (owner_id == '%s' or is_public == true)", 
        currentProjectId, 
        currentUserId
    );

    // 2. 构建搜索请求
    SearchReq searchReq = SearchReq.builder()
            .collectionName("pmo_delivery_docs")
            .data(Collections.singletonList(new FloatVec(queryEmbedding))) // 用户的查询向量
            .annsField("dense_vector")       // 向量字段名
            .topK(10)                        // 返回 Top 10
            .filter(filterExpr)              // 👈 核心：Metadata 权限过滤
            .outputFields(Arrays.asList("doc_name", "chunk_text", "page_number", "doc_type"))
            .searchParams(SearchParam.builder()
                    .metricType(IndexParam.MetricType.COSINE)
                    .params("{\"nprobe\": 10}")
                    .build())
            .build();

    // 3. 执行搜索
    SearchResp searchResp = milvusClient.search(searchReq);
    List<List<SearchResp.SearchResult>> results = searchResp.getSearchResults();
    ```

**2. 这种 Metadata Filtering 会影响 Milvus 的检索性能吗？你在 Java 端/库端做了什么优化？**
*   **参考回答**：
    *   **会影响**。如果是“后置过滤”（先查出 Top 100 向量，再在内存里过滤掉没权限的），会导致返回的结果不足 Top K，且浪费 IO。
    *   **优化方案**：
        1.  **标量索引**：在 Milvus 建表时，必须用 Java SDK 为 `project_id` 和 `owner_id` 字段**显式创建标量索引**（如 `INVERTED` 倒排索引或 `STL_SORT`）。这样 Milvus 底层会先通过倒排索引快速锁定符合条件的文档 ID 集合（BitMap），再在这个小集合里做向量 ANN 搜索（前置过滤 Pre-filtering）。
        2.  **Partition Key (物理隔离)**：对于外包系统，最彻底的做法是在建表时，将 `project_id` 设置为 **Partition Key**。Milvus 底层会自动按项目 ID 哈希分桶。Java 端检索时，虽然不用显式指定 Partition，但 Milvus 引擎会自动利用 Partition Key 裁剪搜索范围，性能提升巨大。

**3. 如果交付经理 A 被调离了项目，权限怎么实时收回？**
*   **参考回答**：
    *   这正是我们采用**查询时动态拼接 Expr** 的优势。
    *   权限数据维护在 MySQL/Redis 中。当 A 被调离，管理员在后台修改了 MySQL 的权限关联表。
    *   A 下次提问时，Java 后端的拦截器（Interceptor）去查权限，发现 A 已经没有 `PRJ-001` 的权限了。
    *   此时，后端要么直接抛出 `403 Forbidden` 异常，要么在拼接 `filterExpr` 时，根本不把 `PRJ-001` 放进去。**Milvus 向量库里的数据一行都不用改**，实现了权限的毫秒级热更新。

### 一、 意图识别与复杂查询路由 (Query Understanding & Routing)

**1. 用户提问：“帮我对比一下 A 项目和 B 项目的延期原因”。这种“跨项目对比查询”，单路 RAG 检索肯定搞不定，系统架构上怎么设计？**
*   **考察意图**：考察复杂查询的路由与多路并发聚合能力。
*   **回答思路**：单路检索会被 Limit（Top-K）截断，导致只召回 A 项目或 B 项目的信息。
    *   **方案（Query Decomposition 查询拆解）**：利用 LLM 将复杂问题拆解为子问题（Sub-queries）：Q1="A项目延期原因"，Q2="B项目延期原因"。
    *   **并发执行**：在 Java 端使用 `CompletableFuture` 并发对这两个子问题执行 RAG 检索（注意：此时 Milvus 的 Filter 表达式需要分别动态切换为 A 项目和 B 项目的权限）。
    *   **聚合生成**：将两路召回的 Context 分别打上 `[Context A]` 和 `[Context B]` 的标签，拼接到 Prompt 中，让 LLM 基于这两份上下文进行对比总结。

**2. 用户的提问往往夹杂非业务问题（如“今天星期几”、“帮我写个 Java 冒泡排序”），如何精准识别意图，防止 RAG 系统“强行回答”导致幻觉？**
*   **考察意图**：考察意图分类（Intent Classification）与 Semantic Router（语义路由）。
*   **回答思路**：不能让所有问题都走 RAG 检索（浪费 Token 且容易答非所问）。
    *   **前置路由**：在请求进入 RAG 链路前，加一层轻量级的意图分类。可以用小参数模型（如 Qwen-7B）或专门的 Embedding 分类器，将 Query 路由到：`[RAG 知识问答]`、`[闲聊/通用大模型]`、`[代码生成]`、`[拒答/越权]`。
    *   只有被路由到 `[RAG 知识问答]` 的 Query，才会触发 Milvus 检索和复杂的 Prompt 组装。

**3. 用户输入模糊查询：“最近项目进度有点慢，咋办？”，没有明确的实体和关键词，向量检索效果很差，怎么优化？**
*   **考察意图**：考察高级检索策略，如 HyDE（假设性文档嵌入）或查询扩展。
*   **回答思路**：模糊查询的向量表示与具体文档的向量表示在空间上距离较远。
    *   **方案（HyDE）**：先不让 LLM 直接回答，而是让 LLM 根据问题**生成一段“假设性的标准答案”**（例如：“项目进度慢通常可以通过增加资源、裁剪非核心需求、优化关键路径来解决...”）。
    *   然后，将这段“假设性答案”进行 Embedding，用**这个向量**去 Milvus 里检索真实的文档。因为假设性答案的语义空间与真实文档更贴近，召回率会大幅提升。

### 二、 检索链路的深度“填坑” (Advanced Retrieval Pitfalls)

**4. 知识库里有很多高度相似的文档（如连续 10 周的周报，格式和套话 80% 相同），导致检索出来的 Top-K 全是重复的废话，怎么解决“同质化文档挤占召回名额”？**
*   **考察意图**：考察对 MMR（最大边界相关性）算法的理解。
*   **回答思路**：纯向量检索（如 Cosine Similarity）只追求“最相似”，会导致 Top-10 全是同一份文档的相邻 Chunk 或高度相似的周报。
    *   **解决**：在向量检索后引入 **MMR (Maximal Marginal Relevance)** 算法进行重排。MMR 在计算得分时，不仅考虑文档与 Query 的相似度，还**惩罚文档与文档之间的相似度**。这样能保证召回的 Top-K 结果既相关，又具备多样性（覆盖不同维度的信息）。LangChain4j 中可以直接配置 MMR 参数。

**5. 对于包含大量 API 接口文档、SQL 语句或代码片段的交付技术文档，普通的文本 Embedding 模型效果很差，怎么处理？**
*   **考察意图**：考察对特定领域（代码/技术）Embedding 模型的选型与分块策略。
*   **回答思路**：
    *   **模型选型**：普通的文本模型（如 bge-large-zh）对代码和 JSON 结构的语义理解较弱。需要替换为专门针对代码微调过的模型（如 `bge-m3` 支持多语言/代码，或 `voyage-code`）。
    *   **分块策略**：代码和 API 文档绝对不能按字符数硬切。必须使用基于语法树（AST）或正则表达式的**语义分块**。例如，保证一个完整的 JSON 报文或一个完整的 SQL 语句不被切断，将其作为一个整体 Chunk 入库。

**6. 向量库（Milvus）返回的 Top-K 结果中，经常混入一些“看起来相关但实际上是历史废弃版本”的文档，除了加 Metadata 过滤，还有什么算法层面的兜底？**
*   **考察意图**：考察 Lost in the Middle（中间丢失）现象及上下文排序。
*   **回答思路**：LLM 对 Prompt 中间部分的注意力较弱（Lost in the Middle）。如果废弃文档混在中间，会干扰生成。
    *   **兜底策略**：在送入 LLM 前，对召回的 Chunks 进行**重排（Reordering）**。将 Rerank 得分最高的 Chunk 放在最前面和最后面（利用 LLM 的首尾注意力机制），得分低的放中间。同时，在 Prompt 中显式加入指令：“*请优先参考时间戳最新（或版本号最高）的文档内容*”。

### 三、 生成控制与格式化输出 (Generation & Formatting)

**7. 业务要求大模型输出的答案必须是严格的 JSON 格式（以便前端渲染成表格或图表），但大模型经常输出多余的 Markdown 标记（如 ```json ... ```）或废话，怎么保证 100% 解析成功？**
*   **考察意图**：考察结构化输出（Structured Output）的工程化控制。
*   **回答思路**：纯靠 Prompt 约束（“请只输出 JSON”）在生产环境中是不够的，必定会有 Bad Case。
    *   **工程解法**：
        1.  **框架支持**：使用 LangChain4j 的 `@P` 注解或 Spring AI 的 `BeanOutputConverter`，底层自动注入 JSON Schema 约束。
        2.  **后处理（兜底）**：在 Java 端写一个健壮的 JSON 提取器。利用正则表达式剥离 ````json` 和 ```` 标记；如果解析失败，将报错信息（如 "JSON 格式错误，缺少括号"）作为 User Message **重新喂给 LLM 让其自我纠正（Self-Correction）**，最多重试 2 次。

**8. 用户要求“根据 PRD 生成一份 5000 字的详细测试用例”，这种超长文本生成，大模型往往会“偷懒”或中途截断，怎么解决？**
*   **考察意图**：考察长文本生成的链路设计。
*   **回答思路**：大模型单次生成的 Token 上限和“注意力衰减”会导致长文本烂尾。
    *   **方案（大纲驱动 + 分步生成）**：
        1.  **第一步**：让 LLM 根据 PRD 生成一份“测试用例大纲（目录）”。
        2.  **第二步**：在 Java 端遍历这个大纲，针对每一个子章节，**循环调用** LLM（传入 PRD 原文 + 当前章节标题），让其生成该章节的具体内容。
        3.  **第三步**：在 Java 内存中将所有生成的章节拼接成完整文档。这样既保证了长度，又保证了每个细节的深度。

**9. PMO 助手需要以“专业、严谨、不带感情色彩”的语气回答，但有时候大模型会突然变得很“热情”（如“好的呢，马上为您解答！”），怎么稳固人设？**
*   **考察意图**：考察 System Prompt 的防御性设计。
*   **回答思路**：
    *   **Few-shot 注入**：在 System Prompt 中不仅规定规则，还要提供 2-3 个**正反例（Few-shot）**。
        *   *反例*：“好的呢，我来帮您看看 A 项目的风险~” -> *纠正*：“A 项目当前存在以下风险：1. ...”
    *   **后置过滤**：在 Java 端配置一个轻量级的正则或文本分类器，如果检测到“好的呢”、“亲”、“没问题”等语气词，自动替换或触发重新生成。

### 四、 性能、成本与工程化体验 (Performance & UX)

**10. 调用大模型 API 时，首字延迟（TTFT - Time To First Token）经常超过 3 秒，用户体验极差，在 Java 后端和前端怎么优化？**
*   **考察意图**：考察流式输出（SSE）及前端交互优化。
*   **回答思路**：
    *   **后端**：绝对不能等 LLM 生成完再返回。必须使用大模型 API 的 **Stream（流式）** 模式。在 Java 端通过 `SseEmitter` (Spring MVC) 或 `Flux` (WebFlux) 将接收到的 Token 实时推送给前端。
    *   **前端/交互**：在等待首字的 3 秒内，前端不要只转圈圈。可以展示 **“思考过程（Thought Process）”**，例如实时打印：“正在检索 A 项目周报... -> 找到 3 份相关文档 -> 正在阅读并总结...”，缓解用户的等待焦虑。

**11. 每次 RAG 检索都要把十几个 Chunk（可能上万 Token）塞进 Prompt，导致 API 调用成本极高，怎么优化 Token 消耗？**
*   **考察意图**：考察 Context 压缩与成本控制。
*   **回答思路**：
    *   **LongLLMLingua / 上下文压缩**：在将 Chunks 送入 LLM 前，加一层“压缩”逻辑。用一个极小、极便宜的模型（或传统 NLP 算法），把每个 Chunk 中与 Query **不相关的句子剔除**，只保留高信息密度的核心句。
    *   **动态 Top-K**：根据 Rerank 的分数动态决定 K 值。如果 Top-1 的分数已经高达 0.95（非常确定），就只送 Top-1 给 LLM；如果分数都在 0.6 左右徘徊，才送 Top-5。

**12. 在 Java 端并发调用大模型 API（如 Map-Reduce 摘要场景），很容易触发大模型厂商的 TPM（每分钟 Token 限制）或 RPM（每分钟请求限制）导致 429 报错，怎么优雅处理？**
*   **考察意图**：考察 AI 应用的限流与重试机制。
*   **回答思路**：
    *   **令牌桶限流**：在 Java 端引入 Resilience4j 或 Guava RateLimiter，根据大模型厂商的配额，在应用层自己做 RPM/TPM 的限流。
    *   **指数退避重试（Exponential Backoff）**：当捕获到 `429 Too Many Requests` 时，不要立即重试。采用指数退避策略（如等待 1s, 2s, 4s, 8s），并加上随机抖动（Jitter），防止多个线程在同一时刻再次打满接口。

### 五、 业务闭环与高阶场景 (Business Loop & Advanced Scenarios)

**13. 知识库刚建立时（冷启动），没有用户反馈数据，怎么评估并优化 RAG 的检索效果？**
*   **考察意图**：考察冷启动策略与合成数据（Synthetic Data）生成。
*   **回答思路**：
    *   **LLM 生成测试集**：写一个脚本，遍历知识库中的核心文档，让 LLM 扮演“挑剔的交付经理”，针对每个文档**自动生成 5 个可能问出的问题及标准答案**。
    *   利用这批“合成数据”构建初始的评估集（Evaluation Set），跑 RAGAS 指标，快速迭代分块和检索策略，度过冷启动期。

**14. 用户在前端对 AI 的回答点了“踩（Thumbs Down）”，这个反馈数据在系统底层是怎么流转并用来优化 RAG 的？**
*   **考察意图**：考察数据飞轮（Data Flywheel）与人类反馈强化学习（RLHF/RAG）的落地。
*   **回答思路**：
    *   **Bad Case 收集**：点踩后，弹窗让用户选择原因（如：答非所问、信息过时、缺少细节），并将 Query、召回的 Chunks、LLM 生成的 Answer 以及用户反馈存入 MySQL 的 `bad_case_log` 表。
    *   **闭环优化**：
        1.  如果是“信息过时”，提醒管理员清理旧文档。
        2.  如果是“答非所问”，人工介入修正该 Query 对应的标准 Chunk，将其加入 **向量库的“强干预/置顶”映射表**（下次遇到相似 Query，强制召回指定 Chunk）。

**15. 交付经理在提问时，经常需要查询实时的外部数据（如：“帮我查一下 Jira 上 A 项目今天还有多少个未解决的 Bug，并结合知识库给出建议”），纯 RAG 做不到，怎么扩展？**
*   **考察意图**：考察 Agent 架构与 Function Calling (Tool Use)。
*   **回答思路**：将系统从纯 RAG 升级为 **ReAct Agent**。
    *   在 Java 端定义 Tools（如 `getJiraBugCount(projectId)`）。
    *   当 LLM 识别到需要实时数据时，会输出 Tool Call 指令。Java 端拦截该指令，调用 Jira API 获取真实数据，然后将数据作为 Observation（观察结果）再次喂给 LLM，LLM 最终结合知识库内容和 Jira 实时数据生成建议。

**16. 如果用户上传了一份包含“公司核心财务数据”或“客户机密代码”的文档，系统如何防止这些敏感信息被大模型“学习”或泄露？**
*   **考察意图**：考察 AI 应用的数据安全与隐私合规（PII 脱敏）。
*   **回答思路**：
    *   **入库前脱敏**：在文档解析后、Embedding 前，引入 NER（命名实体识别）模型或正则规则，将手机号、身份证、核心 IP 地址、财务金额替换为掩码（如 `[PHONE]`, `[IP]`）。
    *   **私有化部署**：对于极度敏感的项目，不调用公有云大模型 API，而是通过 vLLM/Ollama 在本地 GPU 服务器上部署开源模型（如 Qwen-14B），确保数据不出内网。

**17. 知识库里同时存在中文版和英文版的 PRD，用户用中文提问，但召回了大量英文 Chunk，导致大模型中英文混杂回答，怎么优化多语言 RAG？**
*   **考察意图**：考察跨语言检索（Cross-lingual Retrieval）策略。
*   **回答思路**：
    *   **模型选型**：必须使用支持多语言对齐的 Embedding 模型（如 `bge-m3` 或 `multilingual-e5`），确保中英文语义在同一个向量空间。
    *   **Query 翻译/扩展**：在检索前，用 LLM 将中文 Query 翻译一份英文版，**同时用中文和英文去向量库检索**，合并结果。
    *   **Prompt 约束**：在 Prompt 中强制规定：“*无论参考文档是中文还是英文，最终回答必须使用用户的提问语言（中文）进行输出。*”

**18. 用户提问：“A 项目上周的会议纪要里，张三负责的那个模块叫什么？”，这种包含“时间（上周）”和“人物（张三）”的复合条件查询，怎么提高检索精准度？**
*   **考察意图**：考察 Metadata 过滤与向量检索的深度结合（Hybrid Search with strict filters）。
*   **回答思路**：纯向量搜“张三”和“上周”效果很差。
    *   **LLM 实体抽取**：在检索前，用 LLM 或专门的 NLP 工具从 Query 中抽取结构化条件：`{"person": "张三", "time_range": "last_week"}`。
    *   **动态 Filter 拼接**：将抽取的条件转化为 Milvus 的 Filter 表达式（如 `author == '张三' AND create_time >= '2026-06-15'`）。
    *   在这个**严格缩小后的物理范围**内，再对“模块叫什么”进行向量语义检索，精准度极高。

**19. 系统的 RAG 回答有时候会“过度自信”，把知识库里的一句随口吐槽（如“这接口简直反人类”）当成官方结论输出，怎么解决文档可信度问题？**
*   **考察意图**：考察文档权重管理与置信度评估。
*   **回答思路**：
    *   **文档分级**：在 Metadata 中增加 `doc_authority_level`（文档权威度）字段。官方 PRD、架构设计文档设为 High；个人的周报、随意的聊天记录/备忘录设为 Low。
    *   **加权检索**：在 RRF 融合或 Rerank 阶段，给 High 级别的文档增加权重分数。
    *   **Prompt 约束**：提示 LLM：“*当不同文档内容冲突时，请优先采信权威度高的官方文档，并忽略个人主观情绪化的表达。*”

**20. 随着知识库数据量从 10 万条 Chunk 增长到 1000 万条，向量检索的延迟从 50ms 飙升到了 800ms，在不增加硬件成本的前提下，怎么优化？**
*   **考察意图**：考察向量数据库的底层索引调优。
*   **回答思路**：
    *   **索引类型切换**：数据量小时用 `FLAT`（暴力搜索）或 `HNSW`（内存占用大但快）。数据量暴增后，HNSW 会导致内存吃紧且构建慢。可以切换为 `IVF_FLAT` 或 `IVF_PQ`（乘积量化），通过牺牲极少量的精度（PQ 压缩向量维度）来换取检索速度和内存的大幅优化。
    *   **调整 nprobe**：如果是 IVF 索引，动态调整 `nprobe` 参数（搜索时探测的聚类中心数），在延迟和准确率之间找到最佳平衡点。

职责一：文档解析与分块（最容易踩坑、最考察基本功）

❓ 面试官提问 1：你提到针对合同中的“报价清单、付款表格”设计了专属分块策略，具体在代码层面是怎么做的？如果用框架默认的切分，表格会被切碎，你怎么解决？
💡 落地解答思路：
“默认的按字数切分（如 LangChain4j 的 DocumentSplitters.recursive）会把 Markdown 或 HTML 格式的表格拦腰截断，导致大模型丢失表头，无法理解行列对应关系。我的代码实现分两步：”
解析期（识别表格）： 在解析 Word 时，我没有只用纯文本提取，而是使用 Apache POI 遍历文档节点。当识别到 XWPFTable 节点时，我将其单独提取，并转换为 Markdown 格式的表格字符串；对于 PDF，我引入了 Tabula-java 库来专门提取表格区域。
切分期（自定义 Splitter）： 我自定义了一个 Splitter 类实现 DocumentSplitter 接口。逻辑是：将文档拆分为“纯文本块”和“表格块”。
   纯文本：走常规的递归字符切分。
   表格块：将整个表格作为一个独立的 Chunk（文档块）。如果表格特别大（超过了 Token 限制），我的策略是 “保留表头 + 按行切分”，确保每一行数据都带着表头信息存入向量库。

❓ 面试官提问 2：合同通常有严格的章节（如“第一章 商务条款”），你是如何保证分块时不破坏章节语义的？
💡 落地解答思路：
“我采用了基于标题层级（Header-based）的语义切分。”
代码实现： 在解析 Word 时，通过 POI 获取段落的 StyleName（如 Heading 1, Heading 2）。我维护了一个栈（Stack）来记录当前的标题层级路径（例如：["第一章 商务条款", "1.2 付款里程碑"]）。
分块逻辑： 当遇到新的同级或高级标题时，触发分块动作，将之前的文本打包成一个 Chunk，并将当前的标题路径写入该 Chunk 的 Metadata（元数据） 中。这样大模型在回答时，能明确知道这段话属于哪个章节。

职责二：RAG 检索与问答（考察架构设计与调优经验）

❓ 面试官提问 3：你写了“向量检索 + 关键字检索”的混合检索，代码里是怎么融合这两者的分数的？如果向量召回了文档A，关键字召回了文档B，怎么排序？
💡 落地解答思路：
“单纯的向量检索对‘甲方公司简称’、‘特定项目代号’等专有名词效果很差，必须结合 BM25 关键字检索。代码层面我使用了 RRF（Reciprocal Rank Fusion，倒数秩融合）算法 来重新排序。”
代码实现： 
  分别向 PgVector 发起向量检索（取 Top 20）和全文检索（取 Top 20）。
  在 Java 内存中实现 RRF 算法：RRF_score = Σ [1 / (k + rank_i)] （k 通常取 60）。
  将两个结果集按文档 ID 进行 GroupBy，计算每个文档的综合 RRF 分数，然后按分数降序排列，截取 Top 5 喂给大模型。
加分项回答： “如果条件允许，我会在 RRF 排序后，再调用一次 Rerank（重排模型，如 BGE-Reranker），对 Top 5 进行语义级别的二次打分，这样准确率最高。”

❓ 面试官提问 4：大模型很容易产生幻觉（自己编造合同条款），你在 Prompt 和代码链路上是怎么严格限制的？
💡 落地解答思路：
“在严肃的业务系统里，幻觉是零容忍的。我通过系统提示词约束 + 代码层后置校验双管齐下：”
Prompt 强约束： 在 System Prompt 中明确注入规则“你是一个严谨的 PMO 助手。你必须且只能基于 <context> 标签内的信息回答。如果上下文中没有答案，必须回复‘当前项目文档中未查到相关信息’，严禁使用你的预训练知识编造。”
代码层后置校验（Citation Check）： 在流式输出完成后，我会在代码里写一个正则或简单的字符串匹配逻辑，检查大模型生成的答案中，是否包含了上下文中不存在的“关键金额”或“日期”。如果检测到异常数据，系统会自动拦截并返回兜底话术。

职责三：多轮对话与溯源（考察工程细节与用户体验）

❓ 面试官提问 5：多轮对话中，如果用户问“那二期项目的验收标准呢？”，这个“二期项目”在向量库里是搜不到的，你是怎么处理的？
💡 落地解答思路：
“这是典型的多轮对话指代消解（Coreference Resolution） 问题。直接拿用户的原话去搜向量库，什么都搜不到。”
代码实现（Query Rewrite）： 在发起向量检索前，我增加了一个查询重写（Query Rewrite）节点。
  我先用大模型（或轻量级小模型）结合 Redis 中的历史记录（Chat Memory），生成一个独立、完整的查询词。
  比如，将历史问题“A项目的验收标准是什么？”和当前问题“那二期呢？”组合，让大模型重写为“A项目二期的验收标准是什么？”
  拿着重写后的完整 Query 去 PgVector 做 Embedding 和检索，准确率就恢复了。

❓ 面试官提问 6：原文溯源功能是怎么做的？大模型生成的答案，怎么精准定位到原始 Word 文档的某一段？
💡 落地解答思路：
“溯源的核心在于 Metadata 的透传。”
入库时： 文档切块时，每个 Chunk 的 Metadata 里必须包含：doc_id（文档ID）、doc_name（文件名）、chunk_index（块序号）、page_number（页码，PDF特有）。
检索时： 向量检索返回的不仅仅是文本，还有这些 Metadata。
生成与前端展示： 我将检索到的 Chunk 文本和 Metadata 一起拼装进 Prompt。大模型生成答案后，我在 Java 后端将引用的 Metadata 提取出来，组装成 JSON 数组（包含文件名、页码、甚至 MinIO 的预览链接），通过 SSE 和答案一起推给前端。前端在答案末尾渲染成“参考来源 [1]”的可点击角标。

职责四：项目级权限隔离（考察企业级系统开发思维）

❓ 面试官提问 7：外包公司的项目数据是高度保密的，你是如何在代码里实现“交付经理只能看自己项目”的权限隔离的？是在大模型生成后过滤，还是检索前过滤？
💡 落地解答思路：
“必须在检索前（Pre-filtering）进行过滤，如果在生成后过滤，会导致召回的上下文不够，大模型回答质量断崖式下跌。”
代码实现：
  入库阶段： 文档上传时，后端会校验该交付经理的权限，并将 project_id（项目ID）和 manager_id（负责人ID）写入 Chunk 的 Metadata 中。在 PgVector 中，我为 Metadata 字段建立了 GIN 索引。
  检索阶段： 当用户发起提问时，后端先从当前的 JWT Token / SecurityContext 中解析出该用户的 project_ids 列表。
  拼装 SQL/Filter： 在调用 LangChain4j 的 EmbeddingStore.search() 时，传入一个 Filter 对象。底层生成的 SQL 类似于：
     WHERE embedding <=> query_vector < threshold AND metadata->>'project_id' IN ('P01', 'P02')。
  这样从数据库层面就杜绝了越权访问，既安全又保证了召回质量。

❓ 面试题 4：为什么选 PgVector（或 Milvus）做向量库？向量索引你建的哪种？HNSW 和 IVFFlat 有什么区别？
💡 落地解答思路：
    选型理由： “选 PgVector 是因为我们主库就是 PostgreSQL，不需要额外引入和运维新的中间件，且支持 Metadata 的复杂 SQL 联合查询，非常适合初期快速落地。如果是千万级以上数据，我会选 Milvus。”

❓ 1. 大模型返回的 JSON 经常带有 Markdown 标记（如 json ... ）或者多余的废话，导致 Jackson 解析报错，代码层面怎么保证 100% 解析成功？

    交互策略（主动追问）： 让大模型返回一个特定的状态码（如 status: "NEED_MORE_INFO"）和追问话术（如请问是某个具体页面卡，还是整个系统都无法访问？”），前端收到后引导用户补充信息，收集齐了再触发工单创建。

❓ 3. 大模型抽取出的“故障类型”如果不在我们系统数据库预设的枚举字典里，怎么保证数据一致性？

维度二：Agent 工具调用 Function Calling（考察底层原理与边界控制）

❓ 5. 请简述一下 LangChain4j 中 Function Calling 的完整底层执行链路是怎样的？
💡 落地解答： 
    用户发送消息，后端将消息和 Tools 的描述（JSON Schema） 一起发给大模型。
    大模型判断需要调用工具，返回的不是文本，而是 ToolExecutionRequest（包含工具名和 JSON 参数）。
    LangChain4j 框架拦截该请求，通过反射找到 Java 中对应的 @Tool 方法，注入参数并执行本地 Java 代码。
    Java 方法执行完毕，将结果封装为 ToolExecutionResult 再次发回给大模型。
    大模型根据工具返回的结果，生成最终的自然语言回答给用户。

❓ 6. 如果大模型产生了幻觉，乱调用工具（比如用户只是问“今天天气怎样”，大模型却调用了“删除工单”API），怎么防范？
💡 落地解答： 
    工具隔离（按需加载）： 不要把所有工具一次性全塞给大模型。根据用户的初步意图（可通过一个轻量级模型或规则路由），动态注入相关的 Tools。比如闲聊时不注入业务工具。
    危险操作拦截（Human-in-the-loop）： 对于“删除、修改状态、派发”等写操作工具，在 Java @Tool 方法内部增加拦截逻辑。不直接执行，而是生成一个“确认卡片”推给前端，必须由用户点击“确认执行”后，后端才真正落库。

❓ 7. 大模型调用工具时，传入的参数类型错了（比如要求传 Long 类型的工单ID，它传了字符串 "ID123"），导致 Java 反射报错怎么办？
💡 落地解答： 
    严格定义 Schema： 在 @Tool 注解和参数描述中，极其明确地写明类型和格式要求（如 @P("工单ID，必须是纯数字")）。
    全局异常捕获： 在 LangChain4j 的 Tool 执行层配置全局的 ToolExecutionExceptionHandler。当发生参数解析异常时，不要让系统崩溃，而是捕获异常，并将错误信息（如参数格式错误，ID必须为数字”）作为 ToolExecutionResult 返回给大模型，大模型通常会自动纠正参数并重新发起调用。

❓ 8. 如果大模型调用“查询历史工单”工具，但数据库里有几万条，工具把几万条数据全返回给大模型，导致 Token 爆掉（Context Window 超限）怎么处理？
💡 落地解答： 
    工具内部限流： 永远不要把工具当成单纯的 DB 代理。在 @Tool 方法内部，强制加上 LIMIT 分页限制（比如只返回最近的 5 条）。
    数据摘要： 工具返回的不是完整对象，而是经过裁剪的摘要信息（如只返回 {"id": 1, "title": "网络故障", "status": "已解决"}），剔除大段的用户描述和日志，极大节省 Token。

❓ 9. Function Calling 过程中，如果内部 API（如调用外部邮件系统发通知）超时了，大模型一直傻等怎么办？
💡 落地解答： 
    设置超时与熔断： 在 @Tool 方法内部调用外部接口时，必须使用 RestTemplate/WebClient 设置严格的超时时间（如 3 秒）。
    优雅降级： 如果超时，工具不要抛出异常，而是返回一段文本结果："通知服务暂时超时，工单已创建，但邮件未发送成功"。大模型收到这个结果后，会如实向用户转达，保证主流程（创建工单）不被阻塞。

❓ 10. 怎么评估和监控 Function Calling 的成功率和性能？
💡 落地解答： 
    链路追踪： 引入 SkyWalking 或 Micrometer，将“大模型请求 -> 工具解析 -> 工具执行 -> 大模型二次生成”作为一个完整的 Trace 链路。
    关键指标监控： 记录每次 Tool 调用的耗时、参数解析成功率、工具执行报错率。如果发现某个工具（如“自动分配处理人”）经常失败，说明其 Prompt 描述或内部逻辑需要优化。

维度三：工单状态机管理（考察业务架构设计）

❓ 11. 为什么用 Spring StateMachine 来管理工单状态，直接在代码里写 if-else 改数据库状态不行吗？
💡 落地解答： 
    痛点： 工单流转复杂（如：新建->AI预处理->待分配->处理中->待验收->完结），且存在逆向流转（如：打回重审）。if-else 会导致代码极度臃肿，且容易出现“越级流转”的非法状态（如从“新建”直接跳到“完结”）。
    状态机优势： Spring StateMachine 将状态（State）、事件（Event）、转换（Transition）和动作（Action） 解耦。配置好状态图后，框架底层自动校验流转合法性，并能在状态变更时自动触发对应的 Action（如发送通知、调用 AI 接口），代码结构极其清晰。

❓ 12. 如果两个客服同时操作同一个工单（比如一个点击“通过”，一个点击“驳回”），状态机怎么防止并发导致的数据错乱？
💡 落地解答： 
    乐观锁/版本号： 在数据库的工单表中增加 version 字段。状态机触发更新时，SQL 必须带上版本号：UPDATE ticket SET status=?, version=version+1 WHERE id=? AND version=?。
    分布式锁： 在触发状态机事件（Event）的入口，使用 Redisson 分布式锁锁住 ticket_id，确保同一时刻只有一个线程能驱动该工单的状态流转。

❓ 13. 状态机在“AI预处理”状态下，如果大模型 API 宕机了，工单状态卡死在这个节点，怎么设计补偿机制？
💡 落地解答： 
    超时自动流转： 在状态机中配置定时器事件（Timer Event）。如果工单在“AI预处理”状态停留超过 5 分钟，定时器触发，自动将工单流转到“人工兜底处理”状态。
    死信队列补偿： 将失败的 AI 处理任务发送到 RabbitMQ 的死信队列，由后台定时任务扫描重试，或者生成告警邮件发给运维人员。

❓ 14. 工单状态持久化怎么做？每次状态流转都去查数据库吗？
💡 落地解答： 
    StateContext 持久化： Spring StateMachine 提供了 StateMachinePersister 接口。我实现了自定义的 Persister，结合 Redis 缓存当前工单的状态机上下文（Context）。
    读写分离： 读状态时优先走 Redis，只有在触发状态变更事件时，才在事务中将新状态同步写入 MySQL 和 Redis，极大减轻了数据库压力。

维度四：异步处理与限流（考察高并发与系统稳定性）

❓ 15. 为什么大模型调用要用 RabbitMQ 异步削峰？同步调用有什么致命缺点？
💡 落地解答： 
    同步缺点： 大模型 API 响应慢（通常 3~10 秒），如果同步调用，Tomcat 的工作线程会被长时间阻塞。在早高峰报障时，几个并发就能把 Tomcat 线程池耗尽，导致整个系统瘫痪。
    异步设计： 用户提交工单后，后端立刻落库（状态：处理中）并返回成功，同时发一条 MQ 消息。消费者线程以固定的速率拉取消息调用大模型。这样既保护了 Tomcat，又起到了保护大模型 API 不被瞬间打挂的作用。

❓ 16. 你提到用 Redis + 令牌桶算法限流防 Token 超限，具体代码怎么落地的？为什么不用简单的计数器？
💡 落地解答： 
    为什么不用计数器： 固定窗口计数器会有“临界点突发流量”问题（比如限制1分钟100次，用户可能在第59秒和第01秒瞬间发起200次调用）。
    令牌桶落地： 我使用了 Redisson 的 RRateLimiter，它底层就是基于令牌桶实现的。
    代码实现： 在调用大模型 API 的网关层或 Service 层，调用 rateLimiter.tryAcquire(1)。如果获取不到令牌，直接快速失败，返回提示当前系统繁忙，请稍后再试”或将其放入低优先级队列，确保核心 VIP 客户的工单能被优先处理。

❓ 17. 如果 RabbitMQ 消费者在处理 AI 工单时，服务突然重启或宕机了，这条消息会丢失吗？怎么保证不丢？
💡 落地解答： 
    手动 ACK： 消费者绝不能开启自动 ACK。必须在 @RabbitListener 中设置为手动确认模式（AcknowledgeMode.MANUAL）。
    处理逻辑： 只有当大模型成功返回结果，并且工单状态成功更新到 MySQL 后，才调用 channel.basicAck()。如果中途宕机，消息会重新回到 RabbitMQ 队列（或者进入重试队列），等其他存活的消费者继续处理。

❓ 18. 异步处理后，前端怎么知道工单已经处理完了？一直轮询接口吗？
💡 落地解答： 
    拒绝轮询： 轮询太浪费服务器资源。
    WebSocket / SSE 推送： 消费者处理完工单后，不仅更新数据库，还会向 Redis 的 Pub/Sub（或专门的 WebSocket 网关）发布一条事件。前端在提交工单后建立 WebSocket 连接，后端主动将“AI 分类完成，已派发给张三”的结果推送到前端页面，实现实时交互。

维度五：全局架构与综合场景（考察高级排查与优化能力）

❓ 19. 客服反馈：“AI 助手今天给出的工单分类准确率突然变低了”，你作为开发怎么排查这个问题？
💡 落地解答： （体现排查思路）
    查 Prompt 版本： 检查配置中心，看最近是否有人误改了 System Prompt。
    查大模型版本： 确认调用的底层大模型 API 是否被服务商悄悄升级了版本（如从 qwen-turbo 变成了其他版本），导致行为不一致。
    查 Bad Case（坏案分析）： 从数据库导出今天分类错误的工单日志，分析用户的输入是否出现了新的“黑话”或生僻词，导致大模型无法理解。
    查 Few-shot 样本： 检查注入的示例数据是否被污染。找到原因后，补充对应的 Few-shot 样本或微调 Prompt。

❓ 20. 如果公司要求这个 AI 工单系统支持“多租户”（给不同的外包甲方使用），且不同甲方的工单数据、业务字典完全不同，你的架构怎么改造？
💡 落地解答： 
    数据隔离： 数据库表增加 tenant_id 字段，使用 MyBatis-Plus 的多租户插件，在 SQL 层面自动拼接租户过滤条件。
    Prompt 与工具隔离： 在 Redis 中按 tenant_id 隔离存储各自的 Prompt 模板和业务字典。
    动态路由： 在 Agent 执行前，根据当前登录用户的 tenant_id，动态加载该租户专属的 Tools（比如 A 甲方调用 Jira 创建工单，B 甲方调用禅道创建工单），实现一套代码支持多家甲方的定制化业务。

🌟 面试实战建议：
在回答 Agent 和 Function Calling 相关问题时，一定要强调“边界控制”和“兜底策略”。
面试官最怕听到候选人把大模型当成“百分百可靠的上帝”。你必须在回答中反复传递一个理念：“大模型是概率模型，它一定会犯错。我的代码设计，就是为了在它犯错、超时、幻觉时，系统依然能稳健运行，且不会造成脏数据。” 说出这句话，你的技术段位就彻底立住了！
