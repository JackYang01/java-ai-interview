## 1. 真实性规则

所有项目内容只使用四种标签：

- **REAL**：已经明确做过，可以说“项目里做了”。
- **DESIGN**：有完整设计，可以说“如果生产化我会这样做”。
- **LEARN**：学习、源码阅读、Demo 或框架研究。
- **VERIFY**：旧资料冲突或缺少证据，不能直接当项目事实。

没有真实测量数据时，禁止编造：

- QPS；
- P95/P99；
- Recall 提升；
- Accuracy 提升；
- Token 节省比例；
- 故障恢复时间；
- “零事故”；
- “线上提升 xx%”。

## 3. PMO-01 文档进入知识库的完整链路

### REAL 主链

```text
项目文档
  ↓
解析
  ↓
清洗
  ↓
Chunk
  ↓
Embedding
  ↓
索引 / Vector Store
```

### 工程要点

#### 解析

目标不是“把字读出来”，还要尽量保留：

- 标题；
- 章节；
- 表格；
- 文档来源；
- 项目 ID；
- 版本。

#### 清洗

重点删除真正的噪声，而不是破坏语义结构。

#### Chunk

优先依据业务和文档结构。

不要把：

```text
512 Token + 10% overlap
```

背成标准答案。

#### Embedding

模型选型要与：

- 中文能力；
- 文档类型；
- Query 类型；
- 向量库；
- 自己的数据集；

一起评估。

## 4. PMO-02 文档解析异常

典型问题：

- PDF 顺序错乱；
- 表格结构丢失；
- 扫描 PDF 没有文本层；
- Word 标题层级丢失；
- Excel 跨行/跨列语义；
- 超大文件内存压力。

推荐处理：

```text
Upload
 ↓
Parse Job
 ↓
Parser Adapter
 ↓
Normalized Document
 ↓
Validation
 ↓
Chunk
```

生产化 DESIGN：

- 大文件走异步任务；
- Parser 按文件类型隔离；
- 原文件保留到对象存储；
- 每阶段记录状态；
- 失败可定位、可重跑。

不要把 `SXSSFWorkbook` 说成“大 Excel 读取方案”；它主要解决流式写出。

## 5. PMO-03 Chunk 策略

### REAL

项目存在文档切分。

### 设计原则

考虑：

- 标题边界；
- 段落；
- 业务实体；
- 表格；
- Token 上限；
- Parent / Child；
- Metadata。

一个知识单元如果脱离标题后无法理解，可以保留：

```text
项目A > 风险管理 > 供应链风险
```

这样的路径。

### Stable Chunk ID

生产化可以根据稳定业务属性计算 Chunk ID，例如：

```text
documentId + sectionPath + normalizedContentHash
```

不要只依赖易变的数组序号。

## 6. PMO-04 Hybrid Retrieval

### REAL

项目已经明确存在混合检索。

核心原因：

Vector Retrieval（向量检索）和 Keyword Retrieval（关键词检索）各自有盲区。

例如：

```text
“PRJ-2026-017”
```

这种精确标识符未必适合只靠向量语义。

而：

```text
“这个项目为什么延期？”
```

更适合语义召回。

### 当前不能虚构

不能把真实实现自动扩写为：

```text
Milvus + Elasticsearch + BM25 + RRF(k=60)
```

除非后续确认。

### DESIGN：Fusion

两路召回后可以考虑：

- RRF；
- 学习排序；
- Rerank。

但要通过自有数据评估，不固定写死权重。

## 7. PMO-05 多轮 Query Rewrite

### REAL

多轮场景需要把省略和指代补全。

例如：

```text
第一轮：A 项目最近有哪些风险？
第二轮：那进度方面呢？
```

重写为：

```text
A 项目当前在项目进度方面有哪些风险？
```

再进入检索。

### 风险

Rewrite 自己也可能改错。

生产化 DESIGN：

```text
Original Query ─┐
                ├→ Retrieve / Merge
Rewritten Query ┘
```

并记录：

- 原 Query；
- Rewrite；
- 使用的历史；
- 检索结果。

模型自己生成的 `confidence=0.93` 不能直接当可信业务置信度。

## 8. PMO-06 RAG 回答错误排查

固定按链路查：

```text
Source
 ↓
Parser
 ↓
Chunk
 ↓
Rewrite
 ↓
Retrieve
 ↓
Rerank
 ↓
Context
 ↓
LLM
```

### Step 1：Source

原文有没有答案？

### Step 2：Parser

原文解析后是否丢失？

### Step 3：Chunk

答案是否被错误切断？

### Step 4：Rewrite

多轮问题是否被改错？

### Step 5：Retrieve

正确 Chunk 是否被召回？

### Step 6：Context

是否被大量无关内容淹没？

### Step 7：LLM

有正确证据后仍然生成错误答案？

先区分：

- Retrieval Failure；
- Generation Failure。

不要遇到回答错误就第一反应换更贵模型。

## 14. TICKET-01 自然语言 → TicketDraft

推荐主链：

```text
User Text
 ↓
LLM Structured Output
 ↓
TicketDraft DTO
 ↓
Schema Validation
 ↓
Bean Validation
 ↓
Business Validation
```

例如：

```java
record TicketDraft(
    String title,
    String description,
    String priority,
    String assignee
) {}
```

Schema 合法不等于业务正确。

例如：

```text

```

虽然枚举合法，但是否应该是 P0 仍然需要业务规则或人工确认。

## 19. TICKET-06 部分失败

场景：

1. 工单已经创建；
2. 外部通知 Tool 失败。

这不是一句“Retry”就解决。

先明确 Transaction Boundary（事务边界）。

可考虑：

- 本地事务；
- Outbox；
- Saga / Compensation；
- Idempotency；
- MQ。

外部副作用失败时，要知道：

> 哪一步已经真的发生。

## 20. TICKET-07 状态设计

简单业务优先：

```text
enum TicketStatus
+ Domain Service
```

状态复杂后再考虑：

- State Machine；
- Workflow Engine；
- Agent Checkpoint。

不要为了“显得高级”一开始就上 Spring StateMachine。

---

## 21. TICKET-08 RabbitMQ 重投与幂等

如果未来使用 RabbitMQ：

```text
Consumer receives
 ↓
Check idempotency key
 ↓
Already processed?
 ├─ Yes → ACK
 └─ No  → Execute
           ↓
        Persist result
           ↓
          ACK
```

Manual ACK 不等于 Exactly Once。

幂等键应该来自业务语义，例如：

```text
createTicket:userId:clientRequestId
```

而不是通用：

```text
toolName + JSON hash
```

## 23. TICKET-10 宕机恢复

恢复不能只加载 Message History。

正确问题是：

> 上一次已经做了哪些真实副作用？

流程：

```text
Load Checkpoint
 ↓
Check business side effects
 ↓
Decide:
  retry / skip / compensate / manual review
 ↓
Resume
```

如果无法判断某个写操作是否成功，进入：

```text
UNCERTAIN / MANUAL_REVIEW
```

比盲目重试安全。

- Trace；

这一部分用于承接迁移表中原计划放到“源码参考 / 工程交付 / 项目扩展”的内容。当前阶段不再另外拆文件，先保证 00～06 内部知识不丢失。

## 40. PMO 项目的几个非主线扩展场景

### 40.1 长周报 / 多文档摘要：Map-Reduce（DESIGN）

如果一次要总结大量周报、会议纪要或项目文档，可以考虑：

```text
Documents
  ↓
Map：逐文档/逐章节抽取关键事实
  ↓
Structured Intermediate Result
  ↓
Reduce：合并、去重、冲突识别
  ↓
Final Summary
```

不要只保留自然语言摘要。对于进度、风险、负责人、日期等关键字段，可以先形成结构化中间结果，减少多轮摘要的信息损失。

### 40.2 Jira / 工单等实时业务数据：优先 Tool / API（DESIGN）

实时状态不一定适合先同步进 RAG。

例如：

```text
文档知识 → RAG
实时 Issue / Ticket / Progress → Tool / API
```

Agent 或 Workflow 可以在运行时同时使用两类证据。这样比把所有实时数据定时做 Embedding 更容易保证时效性。

### 40.3 Citation 原文锚点与前端高亮（DESIGN / VERIFY）

如果后端返回结构化 Citation：

```json
{
  "documentId": "doc-123",
  "chunkId": "chunk-7",
  "page": 12,
  "startOffset": 320,
  "endOffset": 418
}
```

前端可以支持：

- 点击引用跳转原文；
- 高亮证据区域；
- 展开上下文；
- 显示版本和来源。

它是产品可信度的一部分，但当前 PMO 项目是否真实实现仍按 Fact Sheet 标记，不擅自升级为 REAL。

## 41. MaxKB4j 源码学习点完整保留

这些内容统一标记为 **LEARN**。用途是证明能够阅读开源 Java AI 项目和理解架构，不允许说成“我在自己的生产项目里就是这样实现的”。

### 41.1 Provider 抽象

V1 中关于 Provider 的核心观察保留：

- 上层业务不直接绑定某一家模型 SDK；
- Provider 层封装模型差异；
- 本地模型和云模型可以通过统一上层接口接入；
- 统一接口不等于所有 Provider 能力完全一致。

阅读源码时重点看：

```text
业务层
  ↓
统一 AI 抽象
  ↓
Provider Adapter
  ├─ Provider A
  ├─ Provider B
  └─ Local Provider
```

精确类名和当前分支代码在正式面试引用前必须重新核验。

### 41.2 Document Split / 文档切分

旧题库曾通过类似 `DocumentSplitService` 的实现观察文档切分过程。

保留的学习重点不是背类名，而是看：

- Parser 输出怎样进入 Split；
- Chunk Metadata 怎样保留；
- 不同文档类型有没有差异策略；
- Chunk 与后续 Embedding / Retrieval 如何衔接。

### 41.3 Embedding 抽象

源码学习重点：

- Embedding Provider 怎么抽象；
- Batch Embedding；
- 模型配置；
- 失败处理；
- Vector Dimension 与索引兼容性。

它可以挂到 `RAG-04`，但不能因为源码里存在抽象就声称自己的项目支持多 Embedding Provider。

### 41.4 Data Retriever / Retrieval Routing

V1 中 `DataRetriever` 一类观察点继续保留：

- Query 如何进入 Retriever；
- 不同知识源如何选择；
- Filter / TopK / Search Strategy 怎么传递；
- Retriever 输出如何进入后续 Pipeline。

### 41.5 Composite Store / 组合存储

如果源码存在类似 `CompositeStore` 的组合抽象，要关注的是：

- 为什么需要多个 Store；
- Metadata、全文、向量各自承担什么；
- 一致性和失败边界如何处理。

类名在正式引用前按仓库当前 HEAD 核验。

### 41.6 Hybrid Retrieval

通过源码观察混合检索时，重点分析：

```text
Query
 ├─ Semantic Retrieval
 └─ Keyword / Sparse Retrieval
          ↓
       Fusion
          ↓
        Result
```

不要把源码中的某个固定 TopK、权重或 Fusion 参数提升为行业标准。

### 41.7 Workflow

Workflow 模块的学习价值：

- AI 应用不只有 Chat；
- 节点和边可以表达确定流程；
- Workflow 和 Agent 的边界可以通过源码理解。

### 41.8 Trigger

Trigger 模块说明 AI 能力可以由事件、定时任务、Webhook 等方式启动，而不是只能等待用户在聊天框输入。

### 41.9 工程化观察

源码阅读还应关注：

- 配置管理；
- Provider Registry；
- Error Handling；
- Retry；
- Persistence；
- Tenant；
- Observability；
- API 分层。

### 41.10 MaxKB4j 的优点与不足怎么评价

评价开源项目时不能只说“架构很好”。应分：

- 值得学习的抽象；
- 当前场景为什么这样设计；
- 哪些地方适合自己的项目；
- 哪些地方因为规模、依赖或历史包袱不适合照搬。

## 42. 前端与交付能力知识保留

V1 的 Vue / SSE / WebSocket / Citation UI 等题不再单独占核心母题，但知识点继续保留。

### 42.1 AI 后端和前端的接口不只返回字符串

推荐把流式协议设计成事件：

```text
message.delta
citation.added
step.started
step.completed
tool.started
tool.completed
usage.updated
error
completed
```

这样前端不用猜一段字符串到底是答案、引用还是 Agent 状态。

### 42.2 SSE 和 WebSocket

SSE 适合：

- 服务端 → 浏览器单向推送；
- Token streaming；
- 状态事件。

WebSocket 更适合：

- 高频双向交互；
- 实时协作；
- 客户端持续发送控制消息。

AI 聊天不因为“实时”就必须 WebSocket。

### 42.3 Citation 事件时序

如果答案 Token 先到、Citation 后到，要考虑：

- Citation 对应哪个 message；
- 文本片段位置如何稳定；
- 最终消息完成后是否允许修正 citation；
- 重连后如何恢复事件顺序。

### 42.4 前端不应该持有模型或 Tool 权限

浏览器只负责用户交互。模型 Key、Tool Credential、租户权限和业务授权必须留在服务端。

### 42.5 “全栈”表达边界

Java AI 候选人可以说明自己能定义 API、SSE 协议和前后端协作方式，不需要为了面试把自己包装成专业 Vue 工程师。

## 45. 关于“整合”和“删除”的最终规则

V2 后续维护统一遵循：

> 可以合并重复题，可以改变章节，可以把低频题降为知识卡；但不能因为“不属于49母题”就让知识点消失。

允许删除的只有三类东西：

1. 已确认错误的技术事实；
2. 已过时 API 的错误写法；
3. 无依据的伪生产数字 / 预测 / 营销结论。

即便属于这三类，也要保留对应问题和“为什么错”的纠正知识，而不是把整个主题删掉。

## 46. 场景：金融 / 支付为什么常常是 RAG + 业务流程，而不是纯 RAG

金融、支付、订单类系统通常同时存在两种信息：

### 知识性信息

例如：

- 产品规则；
- 制度；
- FAQ；
- 操作手册。

适合 RAG。

### 实时业务状态和动作

例如：

- 当前余额；
- 支付状态；
- 是否已经退款；
- 风控结果；
- 发起退款。

应该通过 DB / API / Tool 获取或执行。

典型架构：

```text
User
  ↓
Intent / Workflow / Agent
  ├─ Knowledge Question → RAG
  ├─ Real-time Status   → API / DB Tool
  └─ Side Effect        → Authorized Tool + Idempotency + HITL
```

核心边界：

> RAG 负责“找知识”，业务系统负责“给真实状态并执行动作”。不能让模型根据文档猜实时余额，也不能让检索文本直接产生支付副作用。

### 42.6 Vue / Element 这类前端要求在 Java AI 岗位里意味着什么

原 V1 中“为什么 Java AI 岗位会要求 Vue、ElementUI”这个知识点继续保留。它通常不是要求 Java 开发者转成专业前端，而是希望候选人能独立拉通一个 AI 功能模块：聊天页面、知识库管理、Prompt 配置、引用来源、Agent 进度、评测后台等。

Vue 配合 Element UI / Element Plus 只是常见技术组合的例子，真正应该掌握的是：

- REST / SSE / WebSocket 接口联调；
- 流式增量消息渲染；
- Tool / Workflow 中间状态展示；
- Citation（引用）跳转、高亮和上下文展开；
- 错误、取消、重连和完成态处理；
- 前端只展示状态，真正的模型凭证、Tool 权限和业务授权仍由后端控制。
