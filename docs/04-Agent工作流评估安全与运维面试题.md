# Agent工作流评估安全与运维面试题

## 使用说明

本文件覆盖 Java AI 应用最容易决定级别高低的部分：

- 你是不是理解 Workflow 和 Agent 的边界。
- 你知不知道如何做评估、观测、安全和上线治理。
- 你能不能把 AI demo 变成一个可运营、可审计、可扩展的生产系统。

## 一、Workflow 与 Agent

### 1. 什么是 Workflow

答：

- Workflow 更像预先设计好的步骤编排，流程结构相对确定。
- 每一步做什么、什么时候分支、什么时候结束，通常由系统规则控制。
- 它适合稳定任务，例如表单填充、内容审校、审批生成、固定步骤的客服流程。

### 2. 什么是 Agent

答：

- Agent 更强调模型在执行过程中动态做决定，比如选工具、拆步骤、调整路径。
- 它更灵活，但也更难控、更难测、更难审计。
- 所以 Agent 不是“更高级的 Workflow”，而是“更开放的决策体”。

### 3. 为什么说很多场景不需要 Agent

答：

- 因为很多业务流程本来就确定，不需要让模型自由规划。
- 如果工作步骤已知，用 Workflow 通常更稳、更便宜、更容易测试。
- 面试里这样回答会很加分，因为这说明你不是为了炫技而强上 Agent。

### 4. Workflow 和 Agent 的核心差别是什么

答：

- Workflow 的决策更多由代码和规则主导。
- Agent 的决策更多由模型在运行时主导。
- 所以二者最本质的差别是“谁拥有运行时决策权”。

### 5. Prompt Chaining 是什么

答：

- Prompt Chaining 是把复杂任务拆成多个顺序执行的小步骤。
- 前一步输出给后一步作为输入，逐步收敛结果。
- 它比单次超长 prompt 更可控，也更容易定位哪一步出了问题。

### 6. Routing 是什么

答：

- Routing 是把请求按意图、复杂度、语言、成本等级等路由到不同模型或流程。
- 它的价值在于把资源用在最合适的地方，而不是所有请求都走最贵路径。

### 7. Parallelization 为什么重要

答：

- 因为很多子任务可以并行做，例如多维度分析、多工具查询、多候选答案生成。
- 并行化可以降低总耗时，但也会增加编排复杂度和下游压力。
- 所以要配合并发上限、超时治理和结果合并策略一起设计。

### 8. Orchestrator-Workers 模式怎么理解

答：

- 一个中心编排者负责拆任务和聚合结果，多个 worker 执行子任务。
- 这适合复杂任务、批量分析和多角色协作。
- 但要注意不要把它做成“无限递归调用模型”的失控系统。

### 9. Evaluator-Optimizer 模式是什么

答：

- 先生成候选结果，再由评估器判定质量，不合格则继续优化。
- 这种模式能提高结果质量，但一定会增加成本和延迟。
- 所以它更适合高价值任务，不适合所有请求默认开启。

### 10. Agent 设计里，工具是越多越好吗

答：

- 不是。
- 工具越多，模型越难选对，错误调用和越权风险也越高。
- 更好的思路是按场景分层开放工具，控制上下文里的工具集合。

### 11. Agent 的终止条件为什么重要

答：

- 如果没有明确终止条件，Agent 可能陷入反复调用工具、重复推理、成本失控。
- 终止条件通常包括步数上限、时间上限、预算上限、工具结果满足度、人工接管条件。

### 12. 面试里怎么回答“什么时候不用 Agent”

答：

- 流程固定、规则清晰、审计要求高、延迟要求严、成本敏感时，优先 Workflow。
- 只有在任务路径不确定、需要动态规划、需要多工具协作时，才考虑 Agent。

## 二、评估与测试

### 13. 为什么 AI 应用必须做评估

答：

- 因为模型输出不是确定性函数，同样的问题多次调用可能不完全一致。
- 如果没有评估，你很难判断一次模型切换、prompt 修改、工具改动到底是进步还是退步。

### 14. 离线评估和在线评估有什么区别

答：

- 离线评估用固定数据集批量跑，适合版本对比和回归验证。
- 在线评估看真实流量表现，适合观察业务效果、用户反馈和实际稳定性。
- 成熟团队通常两者都要做。

### 15. AI 应用的评估维度通常有哪些

答：

- 任务成功率。
- 结构化输出正确率。
- 工具调用成功率。
- 事实性和一致性。
- 延迟、成本和稳定性。
- 用户满意度与人工复核通过率。

### 16. 为什么不能只靠人工“看着还行”来评估

答：

- 因为人工主观、样本有限、无法高频回归。
- 一旦 prompt、模型、工具链频繁变化，纯人工判断会失去可比性。

### 17. LLM-as-a-Judge 能解决什么问题

答：

- 它可以帮助批量评估回答相关性、格式遵循、事实支持度等指标。
- 好处是速度快、可规模化。
- 但它本身也有偏差，所以不能成为唯一真理，更适合作为评估工具链的一部分。

### 18. 结构化任务怎么做自动评测

答：

- 最适合用字段级比对、schema 校验、枚举正确率、必填项完整率。
- 这种任务比开放式问答更容易建立稳定基准。

### 19. Tool Calling 的评估应看什么

答：

- 工具是否被正确选择。
- 参数是否正确。
- 是否出现多余调用。
- 工具失败后是否正确恢复。
- 最终业务目标是否达成。

### 20. Agent 的评估为什么更难

答：

- 因为它不是只看最终答案，还要看中间路径、工具选择、预算消耗和异常恢复。
- 同一目标可能有多条有效路径，因此评估标准比固定流程更复杂。

### 21. Spring AI 里的评估能力可以怎么理解

答：

- Spring AI 提供了 Evaluator 一类的测试思路，可以用于相关性、事实核验等评测。
- 面试里不需要死背 API，但要知道 Java 生态也在补齐评估和测试链路。

### 22. AI 应用应该怎么做回归测试

答：

- 固定测试集。
- 固定评估维度。
- 记录模型版本、prompt 版本、工具版本。
- 在升级前后做对比，避免“看起来更聪明，实际业务更差”的情况。

## 三、安全与护栏

### 23. 为什么 AI 应用的安全问题和普通 Web 应用不同

答：

- 因为输入不只是参数，还可能包含诱导、绕过、注入和多轮对话污染。
- 输出不只是展示文本，还可能驱动工具、工作流和外部系统动作。
- 所以风险面更大，不是传统接口鉴权做完就够了。

### 24. Prompt Injection 是什么

答：

- Prompt Injection 指用户通过输入诱导模型忽略原本规则、泄露系统信息或执行不该执行的行为。
- 这类风险在 Agent 和工具调用系统中尤其危险。

### 25. 为什么提示词隔离仍然不能完全解决 Prompt Injection

答：

- 因为模型本质上仍然会综合所有上下文去生成结果。
- 即便有角色隔离，也不能把它当成强安全边界。
- 所以需要工具权限控制、输出校验、敏感信息隔离和人工确认共同兜底。

### 26. 工具调用的核心安全风险有哪些

答：

- 越权调用。
- 参数伪造。
- 非幂等操作被重复触发。
- 外部系统被误操作。
- 工具结果把敏感数据反喂给模型。

### 27. 什么是最小权限原则，在 AI 应用里怎么落地

答：

- 只给当前场景必须的工具和数据权限。
- 不同角色、不同租户、不同流程开放不同工具集合。
- 高风险工具要二次确认或人工审批。

### 28. 为什么敏感信息脱敏很重要

答：

- 因为 prompt、日志、工具结果、评估记录里都可能出现账号、手机号、合同信息、内部知识。
- 如果这些内容被直接发往外部模型或写入可观测系统，风险很高。

### 29. 模型输出为什么也要做校验

答：

- 因为模型可能输出危险链接、违规内容、越权指令或非法结构。
- 所以除了输入治理，还要对输出做 schema 校验、敏感词检测、策略过滤和业务规则验证。

### 30. OWASP GenAI 风险框架为什么值得知道

答：

- 因为它帮助你系统化理解生成式 AI 的安全面，不只停留在一句“要防注入”。
- 面试时你只要能说出：AI 安全已经有专门风险框架，覆盖模型、代理、工具和治理，就足够体现视野。

**OWASP GenAI 风险框架 — 精简解读**

它是什么？

OWASP（开放 Web 应用安全项目）专门为生成式 AI / 大语言模型应用制定的安全风险清单，核心产物是 《OWASP Top 10 for LLM Applications》（2023 首发，2025 更新）。

它把 AI 应用的安全威胁系统化分类，不再只是"防 SQL 注入"那套传统思路，而是覆盖 AI 特有的攻击面。

2025 版十大风险（按攻击面速览）
风险   一句话解释
LLM01   提示词注入 (Prompt Injection)   用恶意输入劫持模型行为，排名第一

LLM02   敏感信息泄露   模型吐出训练数据中的隐私/机密

LLM03   供应链漏洞   第三方模型/插件/数据集被投毒

LLM04   数据与模型投毒   训练数据被篡改，模型行为被预埋后门

LLM05   输出不当处理   模型输出未经过滤直接渲染→XSS/SSRF/命令注入

LLM06   过度代理 (Excessive Agency)   Agent 权限过大，能删库、调API、执行任意操作

LLM07   系统提示词泄露   System Prompt 被诱导泄露

LLM08   知识库漏洞   RAG 知识库被注入恶意内容

LLM09   资源消耗失控   恶意请求耗尽 GPU/Token 配额

LLM10   模型拒绝服务   构造超长/复杂输入让模型崩溃

Java 端如何落地？

在 Java（尤其是 Spring AI / LangChain4j）生态中，对应到具体代码层面：

1️⃣ 输入过滤 — 防 Prompt Injection
// Spring AI 的 Advisor 机制，拦截用户输入
@Component
public class PromptInjectionGuard implements CallAroundAdvisor {
    @Override
    public AdvisedResponse aroundCall(AdvisedRequest request, CallAroundAdvisorChain chain) {
        String userMsg = request.userText();
        // 检测恶意注入模式
        if (containsInjectionPatterns(userMsg)) {
            throw new SecurityException("检测到提示词注入");
        }
        return chain.nextAroundCall(request);
    }
}

2️⃣ 输出过滤 — 防敏感信息泄露 & 不当输出
// 对模型输出做脱敏 + 安全过滤
String output = chatClient.prompt()
    .user(userInput)
    .call()
    .content();

// 过滤 PII（身份证、手机号等）
output = piiSanitizer.sanitize(output);
// 防止 XSS：不信任模型输出，转义后再渲染
output = HtmlUtils.htmlEscape(output);

3️⃣ 权限最小化 — 防过度代理
// Agent 调用工具时，严格限定权限范围
@Tool(description = "只读查询订单")  
public List<Order> queryOrders(@Param("userId") String userId) {
    // 只有 SELECT 权限，没有 DELETE/UPDATE
    return orderRepo.findByUserId(userId);
}

4️⃣ 限流与熔断 — 防资源耗尽
// Spring Cloud Gateway / Sentinel 限流
@RateLimiter(value = 10, timeout = 1)  // 每用户每秒最多10次
@PostMapping("/api/chat")
public String chat(@RequestBody String prompt) {
    return aiService.chat(prompt);
}

5️⃣ RAG 知识库防护
入库内容做安全扫描，防止间接注入
检索结果加来源标记，模型输出时区分"知识库内容"与"用户输入"

一句话总结

OWASP GenAI 框架 = AI 应用的安全体检清单。Java 端落地核心就三件事：输入要过滤（Guard Rails）、输出要脱敏（Sanitize）、工具要限权（Least Privilege）。用 Spring AI 的 Advisor 机制 + 传统 Spring Security 的限流/鉴权能力，就能覆盖大部分风险。

### 31. Human-in-the-loop 什么时候必须要有

答：

- 涉及资金、合约、审批、发信、删除、生产环境变更等高风险操作时必须考虑。
- 模型可以生成建议，但最终执行最好由人确认。

### 32. 为什么“让模型自己判断自己是否安全”不够

答：

- 因为模型既是执行者又是裁判者时，可靠性不足。
- 更稳妥的方式是把安全判断外置成规则、审核器、策略引擎或人工复核流程。

## 四、可观测性与成本治理

### 33. AI 应用为什么更需要 Tracing

答：

- 因为一次响应背后可能包含模型调用、工具调用、并行子任务、缓存命中和重试链路。
- 没有 trace，很难知道延迟和故障到底出在哪一步。

### 34. 至少应该监控哪些指标

答：

- 请求量、成功率、失败率。
- 首 token 延迟、总响应时间。
- 输入输出 token 数。
- 工具调用次数、成功率、平均耗时。
- 模型成本。
- 超时和重试比例。

### 35. 为什么 prompt 和 completion 默认不适合全量落日志

答：

- 因为它们通常很长，而且很可能包含敏感信息。
- 所以观测系统要在可排障和数据安全之间做平衡。
- Spring AI 的观测文档也明确强调了这一点。

### 36. 工具参数和工具结果为什么也要谨慎采集

答：

- 工具参数往往就是业务关键数据，例如用户信息、订单号、审批内容。
- 结果里也可能包含内部系统返回值。
- 所以这部分更适合做可控开关和按需采样，而不是默认全量记录。

### 37. AI 应用如何做成本治理

答：

- 模型分层路由。
- token 预算限制。
- 流量分级。
- 缓存与复用。
- 异常重试上限。
- 工具链压缩。
- 对高成本流程设置审批或配额。

### 38. 为什么“只看 API 单价”不等于成本治理

答：

- 因为真正花钱的还有无效重试、冗长输出、多轮工具链、失败补偿和人工介入。
- 所以成本治理必须从链路整体看，而不是只看某个模型每百万 token 单价。

### 39. 如何做 A/B Test

答：

- 固定任务和评估指标，把流量分给不同模型、prompt 或工作流版本。
- 观察效果、成本、延迟和用户反馈的综合结果。
- AI 场景里 A/B Test 往往比“拍脑袋升级模型”更可靠。

### 40. 面试里如何回答“你们怎么排查 AI 线上问题”

答：

- 最好按链路回答：先看 trace，再看模型耗时，再看 token，再看工具调用和异常，再看 prompt/模型版本变更。
- 这种回答会比一句“看日志”专业得多。

## 五、部署、扩容与生产运维

### 41. AI 应用上线前要做哪些准备

答：

- 压测。
- 回归评估。
- 观测埋点。
- 安全策略检查。
- 降级和回滚方案。
- 模型和 prompt 版本登记。
- 成本预估与预算控制。

### 42. 为什么 AI 应用更适合灰度发布

答：

- 因为模型升级、prompt 调整、工具变化都可能带来行为漂移。
- 灰度能让你先在小流量下观察问题，再决定是否全量放开。

### 43. 回滚在 AI 应用里通常回滚什么

答：

- 模型版本。
- Prompt 版本。
- 路由规则。
- 工具定义。
- Agent 策略。
- 所以回滚粒度不能只停留在镜像版本。

### 44. AI 服务扩容为什么不能只靠加 Pod

答：

- 因为瓶颈可能在模型服务本身、GPU、外部工具、数据库、消息队列，而不是 Web 层。
- 如果模型后端吞吐固定，前面加再多应用实例也只是把压力更快打过去。

### 45. 容量规划应该看什么

答：

- 峰值并发。
- 平均与尾延迟。
- 每类任务 token 消耗。
- 工具链长度。
- 模型服务吞吐。
- 冷启动时间。
- 高峰时降级策略是否生效。

### 46. 冷启动为什么是本地模型的重要问题

答：

- 模型加载时间长、权重体积大、显存初始化慢。
- 如果冷启动不可控，弹性扩容效果会很差，用户会直接感知到长时间等待。

### 47. 任务队列在 AI 应用里常见作用是什么

答：

- 把长任务异步化。
- 削峰填谷。
- 支持重试和补偿。
- 解耦前台请求和后台处理。

### 48. 为什么 AI 应用要特别重视幂等性

答：

- 因为一旦重试、超时或 Agent 重复调用工具，就可能重复创建工单、重复发消息、重复扣费。
- 所以对有副作用的工具和任务，一定要设计幂等键和去重机制。

### 49. 怎么把 AI 应用做成可运维系统

答：

- 不是只让它能跑起来，而是要让它能监控、能限流、能回滚、能审计、能追责、能扩容、能止损。
- 这一点其实才是高级面试最看重的地方。

## 六、系统设计高频追问

### 50. 如果让你设计一个企业 AI 助手，先考虑什么

答：

- 先明确任务边界，再明确模型能力，再设计工具边界，再决定流程和状态管理。
- 很多人一上来就说模型选型，这个顺序其实不对。

### 51. 如果要求低延迟，你优先优化哪里

答：

- 优先看模型路由、上下文长度、工具链、流式输出和缓存。
- 如果这些都没做好，直接换更贵模型往往不是最优解。

### 52. 如果要求高可靠，你优先补什么

答：

- 结构化输出。
- 工具权限控制。
- 回归评估。
- trace 和审计。
- 幂等和回滚。
- 人工兜底。

### 53. 如果要求低成本，你怎么做

答：

- 分级路由。
- 历史压缩。
- 结果缓存。
- 控制输出长度。
- 缩短工具链。
- 对低价值请求做降级。

### 54. 如果要求支持本地部署和云部署双模式，你怎么设计

答：

- 统一 Provider 抽象。
- 配置化路由。
- 统一观测与错误模型。
- 区分能力探测和策略选择。
- 不把某一家模型厂商能力写死在业务逻辑中。

### 55. 如果要求可审计，你最少要记哪些信息

答：

- 用户与租户。
- 会话 ID。
- 模型和 prompt 版本。
- 工具调用记录。
- 最终输出。
- 异常和人工干预记录。

### 56. 这一部分最后怎么总结

答：

- Agent、评估、安全和运维这部分，决定你是不是“能把 AI 用在生产里的人”。
- 能力上限靠模型，交付下限靠工程治理。
- 真正的高级回答，一定是把效果、成本、风险、稳定性一起讲清楚。

## 七、招聘导向补充题

### 57. 为什么 2025 到 2026 年的 JD 里，越来越多岗位开始单独写 Agent 平台？

答：

因为很多公司已经不满足于做单个聊天助手，而是在建设可复用的 Agent 基础设施。

Agent 平台岗位出现，通常说明团队已经进入下面这个阶段：

1. 不只想做一个 Demo，而是想支持多个业务场景复用。
2. 不只想接一个模型，而是要做多模型、多工具、多环境治理。
3. 不只想看最终回答，而是要管权限、审计、评测、成本和发布。

所以 Agent 平台本质上不是“把 Agent 放到一个页面里”，而是把下面这些能力平台化：

1. 模型接入与路由。
2. 工具注册与权限控制。
3. 状态管理与记忆管理。
4. 执行轨迹、评测、观测和审计。
5. 工作流与 Agent 的统一编排。

面试里可以一句话概括：

"Agent 平台化的本质，是把原本散落在单个智能体里的能力抽出来，变成整个团队可复用、可治理、可观测的基础设施。"

### 58. 什么是多智能体系统？什么时候值得上，多数时候又为什么不该乱上？

答：

多智能体系统，就是把一个复杂任务拆给多个角色化 Agent 协同完成，比如规划者、执行者、审查者、检索者、代码生成者。

它适合的场景通常有：

1. 任务天然可以分角色协作。
2. 单个 Agent 上下文压力太大。
3. 需要不同技能模块并行处理。
4. 需要评审、复核、对抗或多方案比较。

但多数时候不该乱上的原因也很直接：

1. 链路更长，延迟更高。
2. 成本更高。
3. 路径更难评测。
4. 状态同步和终止条件更复杂。
5. 一旦角色边界不清，很容易变成"多个 Agent 一起放大混乱"。

所以面试里更成熟的说法是：

"多智能体不是默认高级方案，只有在任务确实存在分工价值时才值得上。否则单 Agent 加 Workflow 往往更稳。"

### 59. MCP 为什么会成为越来越多 Agent 岗位里的加分项？

答：

因为企业做 Agent 时，最难的往往不是模型本身，而是怎么把外部工具和数据源稳定接进来。

MCP 的价值在于把"模型怎么发现工具、怎么调用工具、怎么拿到上下文资源"这件事做成相对统一的协议接口。它的工程意义主要有：

1. 降低工具接入成本。
2. 让不同 Agent 或不同客户端共享同一套能力服务。
3. 把工具描述、能力边界和上下文资源管理得更清楚。
4. 让平台型团队更容易做统一治理。

所以面试里不要把 MCP 只说成"一个新协议"，更好的表达是：

"MCP 的价值在于把 Agent 和外部能力之间的连接层标准化，它更像工具生态和上下文资源的接入协议。"

### 60. 什么是上下文工程？为什么它在 Agent 岗位里越来越重要？

答：

上下文工程不是单纯写一句 prompt，而是系统性设计模型在运行时到底能看到什么信息、以什么顺序看到、哪些信息该保留、哪些该裁剪。

它通常包括：

1. 系统指令。
2. 用户输入。
3. 历史对话。
4. 检索结果。
5. 工具定义。
6. 工具返回结果。
7. 记忆和状态。

Agent 岗位越来越重视它，是因为 Agent 的失败很多时候不是因为模型笨，而是因为上下文组织混乱（如历史污染、工具描述冲突、关键指令被淹没）。上下文工程包括：系统指令、动态历史裁剪、RAG 检索结果注入和工具 Schema 管理。

所以一个更工程化的说法是：

"Prompt 工程更像写提示词，上下文工程更像设计模型的运行时信息架构。"

### 61. 技能库或可复用能力模块，在 Agent 系统里应该怎么理解？

答：

技能库可以理解为一组可复用的能力封装，它通常不只是一个 prompt，而是 prompt、工具权限、输入输出约束、执行步骤、失败处理策略的组合。

它的价值在于：

1. 复用成熟能力，避免每个 Agent 重头搭一遍。
2. 提升一致性，减少不同团队各写各的提示词。
3. 便于治理，可以版本化、评测和灰度发布。
4. 更适合平台化沉淀。

所以面试里可以这样讲：

"技能库本质上是在做 Agent 能力组件化，它让智能体开发从临时拼装，走向模块复用和平台治理。"

### 62. 什么叫编码优先 Agent 架构？为什么很多招聘开始点名这类经验？

答：

编码优先 Agent 架构，核心思想是尽量把稳定约束、流程骨架、工具边界、状态机和异常处理放在代码里，而不是全交给模型自由发挥。

它越来越受招聘欢迎，是因为企业已经发现：

1. 纯 prompt 驱动的 Agent 上限高，但下限也很低。
2. 高风险业务需要更强可控性和可测试性。
3. 代码约束比自然语言约束更适合做版本管理、评测和审计。

所以比较成熟的落地方式往往是：

1. 用代码定义主流程和状态边界。
2. 用模型处理不确定性较高的局部决策。
3. 用工具和 schema 控制输入输出。
4. 用评测、回放和灰度机制控制发布风险。

一句话总结就是：

"编码优先不是排斥 Agent，而是把确定性交给代码，把不确定性交给模型，这样系统更像工程产品，而不是实验脚本。"

### 63.中小型AI项目监控与排查方案

这个问题问得非常务实！确实，对于日活几百人的中小型 Java AI 项目，搞一套完整的 OpenTelemetry + Langfuse + SkyWalking + ELK 的"全家桶"，纯属杀鸡用牛刀，不仅开发维护成本高，服务器资源也吃不消。

但即便是中小项目，AI 应用的"黑盒"特性决定了有些东西绝对不能省，否则出了 Bug 你连怎么死的都不知道。

针对中小型项目，我为你总结一套 "极简但保命" 的监控与排查方案：

一、中小型 AI 项目的"三大铁律"

在砍掉复杂的组件之前，我们必须明确 AI 应用与传统 CRUD 应用的不同。AI 应用有三个致命痛点，决定了以下三点绝对不能省：

Token 就是钱（必须记账）
原因：传统应用接口超时只是用户体验差，但 LLM 调用超时或死循环（比如 Agent 陷入 ReAct 循环），后台是在疯狂扣你 API 费用的。
必须做：每一次大模型调用，必须记录 Input Tokens、Output Tokens、使用的模型名，并持久化到数据库。

Prompt 黑盒必须留底（必须留证）
原因：用户投诉"AI 胡说八道"，你如果没有当时的 Prompt 和模型返回的 Completion，你根本无法复现问题。
必须做：记录完整的 Prompt 和 Completion 文本（或至少前几百个字符）。

耗时必须拆分（必须知道慢在哪）
原因：AI 接口慢是常态（通常 5-20秒），但到底是向量库检索慢，还是大模型生成慢？不拆分就不知道优化方向。

二、中小型项目的"极简保命"配置清单

基于以上铁律，以下是中小型 Java AI 项目的最小可行性监控方案（MVP）：
维度   中大型项目   中小型项目（极简方案）   为什么不能省？
链路追踪   OpenTelemetry + SkyWalking   MDC (TraceID) + Logback   保证日志能按请求串起来，这是底线。

AI 专项追踪   Langfuse / Arize   数据库记录 (ChatLog表)   记录 Prompt、Token、耗时，方便复盘和算账。

日志存储   ELK (Elasticsearch)   简单的文件日志 或 轻量级 Loki   必须有地方存日志，文件日志配合 grep 也能干活。

报错通知   复杂的告警路由   钉钉/企微 机器人 Webhook   Token 超标或接口连续报错，必须立刻知道。

服务监控   Prometheus + Grafana   Spring Boot Actuator   至少知道服务死没死、JVM 内存爆没爆。

三、中小型项目"落地三板斧"（代码级实操）

你不需要引入复杂的中间件，只需要用好 Java 生态自带的几个轻量级工具，就能搞定 80% 的排查需求。

第一斧：用 MDC 把日志串起来（零成本）
这是最最重要的一步！不需要任何额外组件，只需要在 Spring Boot 的拦截器/过滤器里加几行代码。

原理：利用 SLF4J 的 MDC（Mapped Diagnostic Context）机制，在请求进来时生成一个 TraceID，塞进线程上下文；在 Logback 配置里把它打印出来。

代码实现：
// 1. 写一个拦截器
public class TraceIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) {
        String traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        MDC.put("traceId", traceId);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();
        }
    }
}

// 2. 修改 logback-spring.xml 的打印格式
<pattern>%d{yyyy-MM-dd HH:mm:ss} [%thread] [traceId:%X{traceId}] %-5level %logger{36} - %msg%n</pattern>

第二斧：建一张"AI 调用流水表"（核心资产）
CREATE TABLE ai_call_log (
  id bigint PRIMARY KEY AUTO_INCREMENT,
  trace_id varchar(32) COMMENT '关联MDC的TraceID',
  user_id bigint COMMENT '哪个用户',
  model_name varchar(50) COMMENT 'gpt-4o / qwen-max',
  prompt_text text COMMENT '发给模型的完整Prompt',
  completion_text text COMMENT '模型返回的内容',
  input_tokens int COMMENT '输入Token数',
  output_tokens int COMMENT '输出Token数',
  duration_ms int COMMENT '模型调用耗时(毫秒)',
  status tinyint COMMENT '1成功 0失败',
  error_msg varchar(500) COMMENT '失败原因',
  create_time datetime DEFAULT CURRENT_TIMESTAMP
);

第三斧：用 AOP 拦截大模型调用（无侵入记录）
Spring AI 底层集成了 Micrometer Observation API，你只需要加一个依赖，它就能自动帮你记录 Token 和耗时。
配合 ai_call_log 表，写一个监听器把 Observation 的数据落库即可。

四、面试中如何回答"中小型项目怎么做监控"？

"对于日活几百人的中小型 AI 项目，我认为没必要盲目追求大而全的可观测性平台，维护成本太高。
但 AI 应用的黑盒特性和成本敏感性，决定了有三样东西是底线，必须做：
日志必须能串联：利用 SLF4J 的 MDC 机制生成 TraceID 并打入日志格式。
AI 调用必须落库：建一张 ai_call_log 流水表，把每次调用的 Prompt、Completion、Token 消耗、耗时存到 MySQL。
异常必须能报警：配合 Spring Boot Actuator 和简单的钉钉/企微机器人，当 LLM 调用失败率飙升或单次调用 Token 异常超标时，立刻推送告警。"

总结
对于中小型 Java AI 项目，记住这个口诀：
"MDC 串日志，MySQL 记 Token，钉钉收告警。"

## 八、Agent 核心架构与运行机制

### 64. 什么是 Agent？它和传统的 Workflow 有什么本质区别？
**面试话术**：
"Workflow 是代码和规则主导的确定性流程，适合步骤固定的任务；而 Agent 是模型主导的开放式决策体。Agent 的核心区别在于它拥有运行时决策权，能够根据环境反馈动态规划步骤、选择工具并自我纠正。"

**技术实现**：
在 Spring AI 中，Workflow 通常表现为硬编码的 `ChatClient` 链式调用；而 Agent 则通过 `ChatClient` 结合 `ToolCallback` 和循环控制来实现。

### 65. 什么是 ReAct 模式？在代码层面是如何实现"思考-行动-观察"循环的？
**面试话术**：
"ReAct 是 Reasoning（推理）和 Acting（行动）的结合。模型先输出思考过程（Thought），然后决定调用什么工具（Action），获取工具返回结果（Observation）后，再进行下一轮思考，直到得出最终答案。"

**技术实现**：
```java
while (step < maxSteps) {
    ChatResponse response = chatClient.prompt().user(context).call().chatResponse();
    if (response.hasToolCalls()) {
        ToolResult result = toolExecutor.execute(response.getToolCalls());
        context.addToolResult(result);
    } else {
        return response.getContent();
    }
}
```

### 66. Agent 在执行复杂任务时极易陷入"死循环"，工程上如何防范和解决？
**面试话术**：
"Agent 死循环会导致 Token 成本失控和响应超时。工程上必须设置硬性熔断机制，包括：最大迭代步数限制、总 Token 预算限制、以及单次请求的全局超时控制。"

**技术实现**：
```java
if (currentSteps >= MAX_STEPS || totalTokens >= TOKEN_BUDGET) {
    throw new AgentTimeoutException("Agent 执行超出预算，强制终止");
}
```

### 67. 什么是"上下文工程"？为什么它在 Agent 开发中比 Prompt 工程更重要？
**面试话术**：
"Prompt 工程是写'怎么问'，而上下文工程是设计模型在运行时'能看到什么信息架构'。Agent 的失败往往不是因为模型笨，而是因为上下文组织混乱。上下文工程包括：系统指令、动态历史裁剪、RAG 检索结果注入和工具 Schema 管理。"

## 九、工具调用 (Function Calling)

### 68. LLM 是如何知道并调用外部工具的？（Function Calling 原理）
**面试话术**：
"模型本身不能执行代码。Function Calling 的原理是：在请求时，我们将工具的名称、描述和 JSON Schema 参数定义作为特殊指令发给模型。模型根据用户意图，生成一段符合 Schema 的 JSON 字符串（Tool Call）。我们的应用层拦截到这段 JSON 后，在本地执行真实代码，再把结果喂回给模型。"

### 69. 如果大模型生成的工具调用参数格式错误（如 JSON 幻觉），工程上如何容错？
**面试话术**：
"模型有时会编造不存在的参数或输出非法 JSON。工程上应引入输出修复机制（Output Parser / Retry）。先尝试用正则或 JSON 修复库进行纠正；如果失败，则将错误信息作为 Observation 返回给模型，让模型自我修正。"

### 70. 当 Agent 可用的工具多达上百个时，如何解决上下文超限和模型"选择困难症"？
**面试话术**：
"工具过多会导致 Token 暴涨且模型选错工具。解决方案是工具路由与动态加载。先用一个轻量级模型（或向量检索）判断用户意图，只加载当前场景相关的 3-5 个工具到上下文中。"

### 71. 如何保证 Agent 调用外部工具时的"幂等性"？
**面试话术**：
"Agent 可能会因网络超时或逻辑错误重复调用同一个工具。对于有副作用的写操作工具，必须在工程上实现幂等性控制，通过传递全局唯一的 TraceID 或业务 Idempotency-Key 到下游系统来实现去重。"

## 十、记忆机制 (Memory)

### 72. Agent 的记忆系统分为哪几种？技术上如何选型？
**面试话术**：
"Agent 记忆分为三类：1. 短期记忆（Working Memory）：当前对话上下文，存在内存或 Redis 中。2. 长期记忆（Long-term Memory）：用户偏好或历史事实，持久化到数据库或向量库。3. 情景记忆（Episodic Memory）：过去的成功/失败经验，用于 Few-Shot 提示。"

### 73. 长对话中，如何优化短期记忆的 Token 消耗？
**面试话术**：
"常用技术是滑动窗口（只保留最近 N 轮）和对话摘要（用小模型把前 N 轮对话压缩成一段摘要）。在 Java 中，可以通过自定义 `ChatMemory` 接口实现这种混合策略。"

### 74. 什么是"向量记忆"？Agent 如何利用它实现经验复用？
**面试话术**：
"向量记忆是将过去的交互或解决方案 Embedding 后存入向量数据库。当 Agent 遇到新问题时，先去向量库检索相似的历史问题，找到高置信度的历史 Solution 后作为 Few-Shot 示例注入 Prompt。"

### 75. 多轮对话中，用户说"把它删了"，Agent 如何准确识别"它"指代什么？
**面试话术**：
"这属于上下文指代消解。工程上应在请求大模型前，加一个前置的'重写节点（Query Rewriter）'。用极低成本的小模型，结合最近 2 轮历史，将指代词改写为具体对象。"

---

## 十一、RAG 与 Agent 的深度融合 (Agentic RAG)

### 76. Agentic RAG 和传统的 Naive RAG 有什么技术区别？
**面试话术**：
"Naive RAG 是'死'的：检索 -> 拼接 -> 生成，一次过。Agentic RAG 是'活'的：Agent 拥有检索工具，可根据问题自主决定要不要检索、用什么关键词检索、检索内容是否足够。"

### 77. Agent 在 RAG 中如何实现"自我反思与检索纠正（CRAG）"？
**面试话术**：
"CRAG 的核心是引入一个评估器节点。检索出文档后，先让轻量级模型评估'这些文档是否足以回答用户问题'。如果评分低，Agent 触发纠正动作：调用 Web Search 或拆解问题重新查向量库。"

### 78. 当 RAG 检索不到答案，或者知识库内容冲突时，Agent 应该怎么处理？
**面试话术**：
"必须有 Fallback 机制。如果检索相似度低于阈值，Agent 应诚实回答'知识库中未找到'。如果是多文档冲突，Agent 应具备交叉验证能力，或在回答中明确列出不同文档的来源和差异。"

## 十二、多智能体协同 (Multi-Agent)

### 79. 多智能体系统有哪些常见的协作拓扑结构？
**面试话术**：
"主要有三种：1. 顺序协作（Sequential）：流水线作业。2. 主管模式（Supervisor）：一个 Boss Agent 拆解任务并路由给不同的 Worker Agent。3. 辩论/对抗模式（Debate）：两个 Agent 扮演不同角色互相挑刺。"

### 80. 在多 Agent 协作中，如何解决"无限互相推诿"或死锁问题？
**面试话术**：
"解决办法是引入全局状态机和强制终止条件。在 Supervisor 模式中，Boss 设定全局最大迭代次数，达到阈值后 Boss 强制接管并输出当前最优解。"

### 81. 什么是 Supervisor 模式？代码层面如何实现 Agent 之间的路由？
**面试话术**：
"Supervisor 模式本质是一个基于 LLM 的动态路由器。Supervisor 的 Prompt 中包含所有 Worker 的名字和能力描述。输出被约束为 JSON（包含 next_agent 和 task_description），代码层解析后传递上下文给对应 Worker。"

## 十四、极致体验：流式、长耗时与状态管理

### 84. Agent 在调用工具时通常需要几秒甚至几十秒，前端如何做到"流式+状态反馈"而不是让用户干等？
* **面试话术**："采用 SSE 或 WebSocket 保持长连接。关键在于事件类型拆分：Agent 开始思考时推送 THOUGHT 事件，决定调用工具时推送 TOOL_CALL_START，工具执行完推送 TOOL_RESULT，生成答案时推送 TEXT_DELTA 实现打字机效果。"

### 85. 遇到需要"人工审批（Human-in-the-loop）"的高危操作，Agent 的线程/状态怎么挂起和恢复？
* **面试话术**："采用状态持久化+事件驱动。当 Agent 决定执行高危工具时，拦截器抛出 HumanApprovalException，将 Agent 当前上下文序列化存入 Redis，生成 approval_task_id 推送给前端。真人同意后后端通过 MQ 发送恢复事件，从断点处继续执行。"

### 86. Agent 单次请求耗时超过 3 分钟，网关和 Nginx 超时怎么解决？
* **面试话术**："绝对不能用同步 HTTP 请求。必须采用异步任务模式。前端发起请求后后端立刻返回 task_id，前端通过轮询或 SSE 订阅任务进度。Agent 执行逻辑丢入线程池或 MQ 异步消费。"

### 87. 多轮对话中，用户中途打断（Cancel）了 Agent 的执行，后端如何优雅中断并清理资源？
* **面试话术**："为每次 Agent 执行分配唯一 execution_id。前端发送 Cancel 时，后端通过 CompletableFuture.cancel(true) 或设置中断标志位。在 ReAct 循环的每一步检查标志位，发现中断立刻清理资源。"

## 十五、核心痛点：上下文爆炸与幻觉控制

### 88. 工具返回了一个几万字的大 JSON 或长文本，直接塞进 Context 导致 Token 超限或模型"迷失"，怎么处理？
* **面试话术**："有三种策略：1. 截断与摘要：用小模型先对长文本做摘要。2. Map-Reduce：分批处理再汇总。3. 结构化过滤：在工具层做预处理，只提取关键字段。"

### 89. 模型在生成最终答案时，无视了工具返回的数据，依然产生幻觉，工程上怎么强约束？
* **面试话术**："在 Prompt 中注入'严格基于上下文回答'的指令。更硬核的做法是引入后置校验：用正则或 NLP 小模型检查答案中的实体/数字是否真的存在于工具返回的 Context 中。"

### 90. 复杂 JSON 解析与容错：模型输出的 JSON 带了 Markdown 标记或者嵌套错误，怎么稳定解析？
* **面试话术**："1. 先用正则剔除 Markdown 代码块标记。2. 使用容错 JSON 库。3. 如果依然解析失败，将错误信息作为 Observation 喂给模型让它自我修复。"

### 91. 生产环境的"幻觉"兜底：如果 RAG 检索不到答案，Agent 应该怎么处理？
* **面试话术**："在 RAG 检索后加一个相关性打分节点。如果检索出的文档相似度得分低于阈值（如 0.6），Agent 走 Fallback 分支回答'抱歉，知识库中未找到相关信息'，不允许模型强行编造。"

## 十六、性能、并发与成本控制

### 92. 多用户同时触发 Agent，底层大模型 API 限流（Rate Limit）怎么处理？
* **面试话术**："在 Agent 和 LLM API 之间加一层智能限流与排队网关。使用 Guava RateLimiter 或 Redisson 进行令牌桶限流；超出请求放入 MQ 削峰填谷。同时配置多模型 Fallback 路由。"

### 93. Token 精确计算与预算控制：怎么在代码里防止单次请求 Token 超支？
* **面试话术**："实现 Token Budget Manager。每次请求分配预算（如 5000 Tokens）。每次 LLM 调用后累加消耗 Token，超过预算 80% 时强制终止循环，用剩余 Token 生成进度总结报告返回给用户。"

### 94. Agent 的缓存机制：相同的 RAG 检索或工具调用，怎么做缓存省钱？
* **面试话术**："采用 Semantic Cache（语义缓存）。将用户 Query 向量化，去 Redis Stack 或 Milvus 中检索相似的历史 Query。相似度 > 0.95 且未过期时直接返回缓存答案，跳过 LLM 调用。"

### 95. 工具调用的超时与重试：Agent 调外部 API 超时了，重试会不会导致重复扣款？
* **面试话术**："工程上必须做到工具层的幂等性。Agent 发起工具调用时自动注入全局唯一的 Idempotency-Key（通常用 TraceID）。外部 API 先查 Redis 是否已处理过该 Key。"

## 十七、框架底层与高级特性 (Spring AI 深度)

### 96. Spring AI 的 Advisor 链是怎么工作的？和 Spring MVC 的 Interceptor 有什么区别？
* **面试话术**：Advisor 是 Spring AI 的核心拦截机制，设计灵感类似 Servlet Filter + AOP Around 通知。
工作方式：多个 Advisor 按 getOrder() 排序组成责任链，请求按顺序穿过每个 Advisor 到达 LLM，响应则逆序返回。每个 Advisor 的 aroundCall() 方法可以在 LLM 调用前修改 Prompt/Message，也可以在 LLM 返回后修改 ChatResponse。
与 MVC Interceptor 的核心区别：
MVC Interceptor 工作在 HTTP 层，操作的是 HttpServletRequest/HttpServletResponse，看到的是 URL、Header、Body 这些原始 HTTP 数据；
Advisor 工作在 AI 语义层，直接操作 Prompt、Message、ChatResponse、ChatOptions 这些 AI 领域对象。
比如我可以用 Advisor 实现：会话记忆注入（在 Prompt 中追加历史消息）、RAG 增强（在请求前检索相关文档注入上下文）、安全过滤（检查输入输出中的敏感词）、日志审计等。这些在 MVC Interceptor 里是做不到的，因为它根本看不到 AI 语义信息

        | 内置 Advisor | 作用 | 阶段 |
        |-------------|------|------|
        | `MessageChatMemoryAdvisor` | 自动把历史对话注入 Prompt | 请求前 |
        | `SimpleLoggerAdvisor` | 记录请求/响应日志 | 请求前 + 响应后 |
        | `SafeGuardAdvisor` | 检测输入中的有害内容 | 请求前 |
        | `QuestionAnswerAdvisor` (RAG) | 从向量库检索相关文档注入上下文 | 请求前 |
        | `ContentFilterAdvisor` | 过滤输出中的不当内容 | 响应后 |

Advisor 比 MVC Interceptor 强大的地方——你在 AI 语义层面进行拦截和增强，而不是在 HTTP 原始数据上做字符串拼接

### 97. Spring AI ToolCallback 原理：底层是怎么把 Java 方法变成 JSON Schema 的？
* **面试话术**："底层核心是 Java 反射 + JSON Schema 生成库。Spring AI 扫描带有 @Tool 注解的方法，通过反射获取方法名、描述、参数类型，利用生成库将 Java Class 结构转换成 JSON Schema 格式。"

### 98. 动态 Prompt 与工具路由：不同权限的用户，看到的工具和 Prompt 不同，怎么动态组装？
* **面试话术**："采用工厂模式+动态路由。请求进入时根据用户 Role 从数据库拉取对应的 System Prompt 和 Tool 列表，运行时动态构建 ChatClient。"

### 99. 向量检索不准（RAG 痛点）：单纯的向量检索召回率低，怎么结合 BM25 做混合检索？
* **面试话术**："同时发起两路查询：向量库（Dense）和 ES BM25（Sparse）。通过 RRF（Reciprocal Rank Fusion）算法对两路结果重新计算和排序，大幅提升召回准确率。"

### 100. 多模态 Agent 处理：不仅要处理文本，还要处理图片/PDF，上下文怎么管理？
* **面试话术**："图片：先经本地视觉模型提取关键文本或特征，再作为文本注入 Context。PDF：使用解析工具转为 Markdown 并进行分块（Chunking），结合 RAG 检索相关片段。"

### 101. 多 Agent 通信与状态共享：多个 Agent 之间怎么传递上下文？共享内存还是消息传递？

### 102. 意图漂移（Intent Drift）：多轮对话中，模型聊着聊着忘了最初的目标，怎么拉回来？
* **面试话术**："1. 上下文重排：将核心 System Prompt 和用户初始目标动态移动到 Message 列表末尾。(System Prompt 和用户初始目标一般要缓存)
                2. 目标反思节点：每隔3轮插入反思 Prompt，检查是否偏离初始目标。"
* **补充问题**：“既然每次全量传入了上下文，为什么还会意图漂移？” 你可以这样回答，绝对能让面试官眼前一亮：
        **答**：“从工程接口层面看，每次确实全量传入了历史上下文，物理上没有丢失。但意图漂移的本质不是数据丢失，而是大模型注意力机制的缺陷导致的语义忽略。
                主要有三个原因：第一是 ‘*Lost in the Middle*’，随着对话变长，初始目标被挤到上下文中间，注意力权重下降；
                               第二是*近因效应*，模型容易被最近几轮的局部对话带偏，忽略了全局约束；
                               第三是*长上下文带来的注意力稀释*。
                所以，为了解决这个问题，我们不能仅仅依赖模型原生的注意力，必须在工程上做干预。比如上下文重排，把核心目标动态提取出来放到 Message 列表的末尾，利用近因效应强化约束；或者在 Agent 流程中引入反思节点，定期强制模型对比当前状态和初始目标，从而把漂移的意图拉回来。

### 103. Agent 评测自动化：线上怎么自动收集 Bad Case 并做回归测试？
* **面试话术**："1. 录制：将线上每次请求的 Input、Tools 调用轨迹、Final Output 异步写入日志。
                2. 打分：每天用 LLM-as-a-Judge 对记录打分。
                3. 回归：将低分记录加入测试集，每次修改 Prompt 或升级模型后跑自动化测试集。"

### 104. Agent 评测自动化执行在什么阶段？

答：是贯穿全生命周期的。

- 在测试阶段，它是 CI/CD 的质量门禁，每次改动都会跑黄金测试集，不达标就阻断发版。
- 在线上运行后，它也会每天和正式系统同时跑，但架构上做了严格的异步旁路解耦。主链路把 Trace 日志异步扔到 Kafka，评测系统在后台消费打分，完全不影响线上延迟。
- 最关键的是形成了一个数据飞轮：线上旁路捞出的真实 Bad Case，修正后会自动回流到测试集里。这样我们的测试集是跟着真实业务动态生长的，越跑越厚，实现了 Agent 能力的持续迭代。

## 十九、补充高频题（原文档遗漏）

### 105. ReAct、Plan-and-Execute、Reflexion 三种范式怎么区分？

答：

- **ReAct**：边想边做，Thought → Action → Observation 循环，适合工具路径不确定的任务。
- **Plan-and-Execute**：先出计划再执行，适合步骤可预估、需要 prioritization 的长任务；计划可失效需重规划。
- **Reflexion**：对失败轨迹做反思并改进下一轮策略，适合可反复试错的离线/批处理，不太适合强实时交互。
- 选型原则：路径越不确定越偏 ReAct；审计和步骤越固定越偏 Workflow / Plan。

### 106. Agent 状态机为什么比“纯聊天消息列表”更适合生产？

答：

- 消息列表适合对话展示，不适合表达“当前停在审批节点 / 等待工具 / 已取消”。
- 状态机可以明确：RUNNING、WAITING_HUMAN、WAITING_TOOL、SUCCEEDED、FAILED、CANCELLED。
- 挂起恢复、幂等重试、超时清理都依赖显式状态，而不是从聊天记录反推。

### 107. 什么是间接 Prompt Injection？和直接注入有什么不同？

答：

- 直接注入：用户在输入里写“忽略以上规则”。
- 间接注入：恶意内容藏在网页、邮件、知识库文档、工具返回里，模型读取后被劫持。
- RAG/Agent 场景更危险，因为“检索到的内容”常被默认信任。
- 防护：对外部内容做不可信标记、工具结果清洗、高危动作二次确认、知识库入库扫描。

### 108. AI 应用的可观测性最少要接哪些“语义约定”字段？

答：

- trace_id / span：覆盖 rewrite、retrieve、rerank、llm、tool。
- gen_ai 相关属性：model、temperature、input/output token、finish_reason。
- 业务属性：tenant、app_id、prompt_version、tool_name、cache_hit。
- 目标：既能算成本和延迟，又能回放一次失败请求的完整路径。

### 109. 多租户 Agent 平台最容易翻车的 3 个点是什么？

答：

1. 工具权限按用户/租户动态装配失败，导致越权。
2. Memory / Cache key 没带 tenant，造成会话或答案串租户。
3. 成本与配额没按租户隔离，一个租户打爆共享额度。

### 110. 什么时候该把 Agent 执行改成“工作流节点 + 少量 LLM 决策”？

答：

- 当 80% 路径已经稳定、只有少数分支需要模型判断时。
- 用 Workflow 固化主干，用 LLM 只做分类/抽取/局部规划，通常更便宜、更好测、更好审计。
- 面试加分句：**先把确定性步骤收回代码，把不确定性留给模型，而不是反过来。**
