# 大模型基础与能力面试题

## 使用说明

本文件聚焦“非 RAG”的大模型基础能力，解决的是下面这类面试追问：

- 你到底懂不懂大模型本身，而不只是会调接口。
- 你知不知道模型为什么会快、会慢、会贵、会胡说。
- 你能不能说清楚模型选型、量化、微调、多模态和服务化的基本逻辑。

## 一、模型基础认知

### 1. 什么是大语言模型

答：

- 大语言模型本质上是对海量文本分布进行建模的神经网络，它的核心能力是“根据上下文预测下一个 token”。
- 因为训练数据和参数规模足够大，它不仅能补全文本，还会表现出问答、总结、翻译、代码生成、分类、规划等泛化能力。
- 面试里要强调：LLM 不是规则引擎，也不是数据库，它擅长概率生成，不擅长天然保证事实正确。

### 2. 为什么 Transformer 是大模型的核心架构

答：

- Transformer 的关键是自注意力机制，它能在一次前向过程中让一个 token 关注上下文里的其他 token。
- 相比 RNN，Transformer 更适合并行训练，因此可以把模型规模、数据规模、训练算力一路放大。
- 大模型很多能力提升，本质上都建立在 Transformer 可扩展这一前提之上。

| 特性 | RNN / LSTM | Transformer | 对大模型的影响 |
| :--- | :--- | :--- | :--- |
| 计算方式 | 时序串行，难充分并行 | 序列内可并行计算注意力 | 更容易利用大规模 GPU 集群做预训练 |
| 长程依赖 | 远距离信息易衰减 | 任意位置可直接建立注意力连接 | 更适合建模长文本与复杂上下文 |
| 扩展性 | 训练吞吐与规模受限 | 规模化训练路径更成熟 | 支撑参数量与数据量同步放大 |

Transformer 之所以成为主流底座，是因为它在「语言建模能力」和「硬件可扩展训练」之间找到了更优平衡；但不等于没有上限——显存、注意力复杂度、长上下文利用率仍然是工程约束。


### 3. token 是什么，为什么它比“字数”更重要

答：

- 模型看到的最小处理单位不是“字”或“单词”，而是 token。
- 成本、延迟、上下文长度、输出长度，最终几乎都按 token 计量。
- 面试时最好顺带说明：中文、英文、代码、表格的 token 化效率不同，所以同样的文本长度，token 成本可能差很多。

### 4. tokenizer（分词器） 的作用是什么

答：

- tokenizer 负责把自然语言切成 token，并在生成后再还原成人可读文本。
- 它会直接影响上下文利用率、成本估算和模型兼容性。
- 两个模型即便参数规模类似，只要 tokenizer 不同，处理同一份文本的 token 数也可能差异明显。
- Tokenizer（分词器）确实与特定的大模型是深度绑定的。
    你通常**不需要**从零开发一个 Tokenizer，
    但在实际应用中，往往需要根据业务场景进行“定制”或“微调”，
    比如涉及医疗、法律、金融代码等专业领域，
    在保留原有的 Tokenizer 规则的前提下，将你的行业术语（如“非小细胞肺癌”、“质押式回购”）作为新词加入词表
    关键步骤： 添加新词后，必须调整模型的 Embedding 层（嵌入层）大小，并对这些新词进行少量的继续预训练或微调，让模型学会这些新词的语义。

| 开发阶段 | 是否需要动 Tokenizer？ | 操作建议 |
| :--- | :--- | :--- |
| API 调用 / 简单推理 | 否 | 直接用厂商提供的工具库，不要尝试修改。 |
| 基于开源模型微调 | 视情况而定 | 如果领域跨度大（如从写小说变成写代码），建议添加领域专有词汇到词表中。 |
| 从头预训练模型 | 是 | 必须根据你的训练数据集，训练一个匹配的 Tokenizer。 |



### 5. 什么是上下文窗口

答：

- 上下文窗口就是模型**单次请求**里最多能同时看到多少 token。
- 它决定了你最多能塞进去多少系统提示词、历史消息、工具结果和用户输入。
- 面试官常追问的一点是：上下文窗口变长，不等于模型一定更聪明；它只是“能看更多”，不代表“能稳定利用更多”。

### 6. temperature、top_p、top_k 分别控制什么

答：

- temperature 控制随机性，越高越发散，越低越稳定。
- top_p 是核采样，表示只从累计概率达到某阈值的候选 token 中采样。
- top_k 是只保留概率最高的前 k 个 token 再采样。
- 工程上常见策略是：事实型任务把 temperature 调低，创意型任务适当放高，但不要多参数一起乱调。

### 7. max_tokens 为什么很关键

答：

- 它限制**输出上限**，直接影响响应长度、成本和延迟。
- 如果设置太小，答案可能被截断；设置太大，模型会有更大生成空间，成本和耗时也会增加。
- 面试里要体现出工程意识：max_tokens 不是越大越好，而是应按任务类型设置预算。

### 8. System Prompt、User Prompt、Tool Message 分别是什么

答：

- System Prompt 决定**角色、规则和回答边界**。
- User Prompt 是**当前任务**本身。
- Tool Message 是外部**工具返回**的结构化**结果**，供模型继续推理。
- 一般要向面试官说明：系统提示词更像“策略层”，用户输入更像“任务层”，工具结果更像“外部事实层”。

### 9. **什么叫幻觉**

答：

- 幻觉就是模型给出了看似合理、实则**不可靠**或**不真实**的内容。
- 根因通常包括：**训练分布限制、上下文不足、提示词不清、工具/外部事实缺失、采样过于发散**。
- 工程上不要把“让模型别幻觉”当成一句 prompt 就能解决，而要通过**约束输出**、**工具调用、校验和评估**来一起控制。

工程上控制幻觉，通常靠四件套一起做，而不是只靠一句“请不要胡说”：

1. **约束输出**：用 JSON Schema / Structured Output / 受约束解码，先把格式框死。
2. **工具调用**：把实时事实和业务数据交给工具拿，模型负责调度而不是瞎编。
3. **校验**：Schema 校验 + 业务规则校验 + 高风险操作人工确认；失败可把错误回喂模型做一次修复。
4. **评估**：用离线评测集和线上抽样，盯准确性、工具调用成功率、幻觉率、延迟，形成迭代闭环。

一句话：**约束管格式，工具管事实，校验管边界，评估管是否真的变好。**

### 10. 推理模型和普通聊天模型有什么区别

答：

- 普通聊天模型更偏通用对话和直接生成。
- 推理模型通常更擅长多步分析、规划和复杂问题拆解，但代价可能是更慢、更贵。
- 面试中应给出取舍：简单问答不要强上推理模型，复杂流程编排、代码分析、策略规划更适合推理能力更强的模型。

### 11. 开源模型和闭源模型怎么选

答：

- 闭源模型通常在**综合能力、稳定性、多语种、工具调用生态**上更成熟。
- 开源模型优势是可**私有**化、**可控**性高、可**量化**、可**定制**、**成本**可优化。
- 选择依据应包括：效果、延迟、成本、数据合规、是否需要本地部署、是否需要可解释和可控的生命周期。

### 12. 云模型和本地模型怎么选

答：

- 云模型适合快速上线、弹性使用、前期试错，省去推理服务运维成本。
- 本地模型适合数据敏感、成本长期可预测、需要离线能力或需要深度定制的场景。
- 实际项目里常见做法是分层：高价值复杂任务用云模型，低成本或隐私任务用本地模型。

## 二、训练、对齐与模型适配

### 13. 预训练是什么

答：

- 预训练是让模型在**海量语料**上**学习语言规律和世界知识**的阶段。
- 它决定了模型的通用语言理解和生成底座。
- 对应用工程师来说，不一定亲自做预训练，但必须知道大多数能力都来自这一阶段，而不是后面的 prompt 魔法。

### 14. SFT 是什么

答：

- SFT 指**监督微调**，用人工标注的问答、指令、对话样本继续训练模型。
- 它主要解决“会不会按要求回答”“风格是否符合任务”的问题。
- 面试时可强调：很多业务场景优先考虑 prompt 优化、结构化输出、工具调用，只有格式和领域行为长期不稳定时才考虑 SFT。

### 15. RLHF 是什么

答：

- RLHF 指基于**人类反馈的强化学习**，通过**偏好数据**让模型更符合人类期望。
- 它主要改善有用性、无害性、对齐程度，而不是简单提高知识量。
- 面试中不必展开算法细节，但要能说出它解决的是“**价值对齐**”和“**偏好优化**”。

### 16. DPO 是什么，为什么现在常被提到

答：

- DPO 是一种**直接偏好优化**方法，不需要像传统 RLHF 那样完整构建强化学习流程。
- 它工程上更简单，训练稳定性和实施成本通常更友好。
- 面试里可以概括为：**DPO 是对齐阶段更实用的一条路线，很多团队更容易落地**。

| 特性 | RLHF (以PPO为例) | DPO |
| :--- | :--- | :--- |
| 训练复杂度 | 高，需要协调策略、价值、奖励等多个模型 | 低，单阶段训练，只需策略和参考模型 |
| 内存占用 | 高，需同时加载多个大型模型 | 中等，仅需加载两个模型 |
| 稳定性 | 较低，PPO对超参数非常敏感，训练易崩溃 | 较高，类似监督学习，非常稳定 |
| 实现难度 | 高，需要深厚的强化学习背景 | 中等，有Hugging Face等成熟库支持 |
| 数据需求 | 需要在线采样和奖励标注 | 离线，直接使用准备好的偏好数据 |



### 17. Base Model、Instruct Model、Chat Model 的区别是什么

答：

- Base Model 更像**原始语言分布建模器**，不一定善于听指令。
- Instruct Model 经过指令微调，更**擅长执行任务**。
- Chat Model 通常进一步围绕多轮对话、人机交互、对齐策略做优化。
- 项目中一般不会直接把 base model 暴露给业务用户。

### 18. 什么叫对齐

答：

- 对齐就是让模型输出更**符合人类**目标、规则和使用边界。
- 它包含有用性、诚实性、安全性、格式遵循、拒答策略等多个维度。
- 你要向面试官表达清楚：对齐不是“更聪明”，而是“**更可控**、**更像产品能力**”。

### 19. Prompt Engineering 和 Fine-tuning 该怎么取舍

答：

- 如果问题是任务说明不清、格式不稳定、步骤没约束，优先改 prompt。
- 如果问题是领域风格长期固定、输出行为需要稳定收敛、样本分布很明确，才考虑微调。
- 多数应用团队的正确顺序是：**先 prompt，再结构化输出，再工具和工作流，最后才考虑微调**。

### 20. LoRA/PEFT 是什么

答：

- **PEFT 是参数高效微调，LoRA 是其中最常见的方法**。
- 它不是全量改模型参数，而是在**较小的增量参数**上学习，从而降低训练成本和显存需求。
- 工程价值在于：更便宜、更快、更容易为不同业务维护多套适配版本。

### 21. 蒸馏是什么

答：

- 蒸馏是让小模型学习大模型的行为，从而在较低成本下保留部分能力。
- 常见目标是降低延迟和推理成本，而不是追求绝对上限能力。
- 面试里可以把它理解成“**用大模型教小模型**”，适合高并发、低延迟、固定任务场景。

### 22. 量化和微调是什么关系

答：

- 微调是**改模型行为**，量化是**压缩模型**表示和推理成本。
- 两者可以组合，但目标不同。
- 一般可用一句话讲清：微调解决“像不像我要的助手”，量化解决“跑不跑得动、跑得贵不贵”。

### 23. 什么时候不建议微调

答：

- 数据量不够、标注质量不稳、需求变化快、任务边界模糊时，不建议急着微调。
- 如果问题来自工作流设计、工具缺失、输出约束不足，微调通常治标不治本。
- 面试里这样回答会显得你有成本意识，而不是为了炫技盲目上训练。

### 24. 企业里为什么经常先做模型路由，而不是先做训练

答：

- 因为很多问题可以通过模型分层解决，比如简单任务走便宜模型，复杂任务走强模型。
- 这种方式落地快、试错便宜、可灰度切换。
- 对业务团队来说，模型路由通常比自建训练体系更符合 ROI。

## 三、推理性能与成本控制

### 25. 什么是 TTFT 和 TPS

答：

- TTFT 是 first token latency，也就是首 token 时间，影响“快不快开始回复”。
- TPS 通常指 tokens per second，影响整体输出速度。
- 面试时要说明：用户体感通常先受 TTFT 影响，长回答或多轮任务再明显受 TPS 影响。

### 26. KV Cache 是什么

答：

- KV Cache 会缓存 Transformer 注意力计算中**历史 token** 的 key/value，避免每次生成都重复算整段上下文。
- 它是推理性能优化的基础设施之一。
- 你可以把它理解成“复用历史计算结果”，上下文越长，这类优化越重要。

### 27. 什么是 batch 和 continuous batching

答：

- batch 是把多个请求一起送进推理引擎，提高硬件利用率。
- continuous batching 是更动态的批处理方式，可以在**解码过程中持续接入新请求**。
- 这类能力是高并发模型服务的关键，很多高性能推理框架都围绕它做优化。

### 28. Prompt Caching 是什么

答：

- Prompt Caching 指对重复前缀或相似上下文进行复用，减少重复计算和成本。
- 适合系统提示词很长、固定前缀很重、重复任务多的场景。
- 面试里可以补一句：缓存命中不稳定时，不要把它当唯一优化手段，要结合路由、裁剪和流量治理。

### 29. 为什么上下文越长，成本和延迟通常越高

答：

- 输入 token 多，前向计算自然变重。
- 历史越长，注意力开销越大，显存占用和吞吐也会受到影响。
- 所以真实工程里一定要做上下文预算，不能把“长上下文”当无限资源。
- 常见的优化策略包括：
    智能截断与摘要：不把所有历史都塞进上下文。对于很久之前的对话，可以用一个更小的模型进行摘要，只保留核心信息。
    选择性检索 (RAG)：与其提供全部背景知识，不如根据当前问题，从海量文档中精准检索出最相关的几个片段作为上下文。
    采用高效注意力算法：使用如 FlashAttention 等优化算法，它们通过改变计算顺序和利用GPU的高速缓存，显著减少了标准注意力机制的内存访问次数，从而大幅提升速度和效率。
    滑动窗口：只保留最近的 N 轮对话，让更早的历史自然“滑出”窗口。

### 30. 流式输出为什么常见

答：

- 它能显著降低用户感知等待时间，因为首 token 一出来，前端就开始显示内容。
- 对聊天、代码补全、长文生成这类场景，流式体验往往比总耗时更重要。
- 但流式输出也会带来前后端协议、连接保持、内容中断恢复、审计记录等额外问题。

### 31. 量化是什么

答：

- 量化是把**模型参数用更低精度表示**，例如 8bit、4bit，甚至更低位宽。
- 目标是减少显存和内存占用，提高推理可部署性。
- 代价通常是能力有损失，所以量化本质上是“效果换成本”的工程取舍。

### 32. 本地部署模型时，硬件要看什么

答：

- 先看模型参数规模与量化后体积，再看显存或内存是否装得下。
- 再看吞吐需求、并发量、是否需要多实例扩展。
- 如果是边缘部署，还要考虑 CPU 推理、功耗、启动时间、磁盘体积和平台兼容性。

### 33. llama.cpp、Ollama、vLLM、Xinference 大致怎么理解

答：

- llama.cpp 更偏**底层高性能本地推理能力**，强调广泛硬件支持、GGUF、量化、本地部署。
- Ollama 更像**开箱即用**的本地模型运行层，适合快速拉起模型和标准化接口。
- vLLM 更偏**高吞吐服务化推理**，强调连续批处理、KV Cache 管理等服务端性能。
- Xinference 更偏**统一模型服务平台**，可以托管多种模型类型和运行后端。
- 面试里不必卷源码细节，但要能讲出它们服务的不是同一层问题。

### 34. 如何做模型基准测试

答：

- 不能只看主观感觉，至少要看首 token 延迟、整体吞吐、并发表现、稳定性和成本。
- 还要按任务测，比如结构化抽取、工具调用、代码生成、多轮对话，不同任务结果可能完全不同。
- 如果是生产系统，还要测冷启动、超长输入、超时比例和降级表现。

### 35. 为什么有些模型“看起来便宜”，但总成本并不低

答：

- 单价低不代表总成本低，因为如果回答啰嗦、失败率高、工具调用反复重试，总 token 和调用次数会飙升。
- 模型效果不稳定还会带来人工复核成本和用户流失。
- 所以真正的成本是“模型单价 + 重试 + 工具链 + 人工干预 + 故障代价”的总和。

## 四、多模态与扩展能力

### 36. 什么是多模态模型

答：

- 多模态模型指可以处理文本之外的数据形式，例如图像、音频、视频、文档版面等。
- 它让 AI 应用不再只停留在聊天，而能覆盖 OCR、视觉问答、语音助手、图像生成等场景。
- 面试里最好表达清楚：多模态不是“多放几种文件”，而是输入输出能力边界被扩展了。

### 37. 语音 AI 应用通常由哪些环节组成

答：

- 一般是 ASR 把语音转文本，LLM 做理解与推理，再由 TTS 把结果转回语音。
- 如果需要实时双工对话，还要解决打断、回声抑制、低延迟传输和会话状态同步。
- Java 侧常承担网关、编排、状态管理和业务逻辑，不一定自己做底层声学模型。

### 38. OCR 和文档解析在 AI 应用里为什么重要

答：

- 因为很多企业数据并不是干净文本，而是 PDF、扫描件、表单、图片、合同、票据。
- 如果前处理差，后面无论是问答、抽取、审校还是工作流自动化，质量都会受影响。
- 所以面试里可以强调：AI 应用往往不是只有模型，文档理解链路同样关键。

### 39. 图像生成和文本生成在工程上有什么不同

答：

- 图像任务通常更重资源、更依赖异步任务和结果存储。
- 请求参数也更像“作业配置”，例如尺寸、风格、种子、响应格式，而不是单纯 prompt。
- 这决定了后端设计上更偏任务系统，而不是简单同步请求。

### 40. 代码模型在企业里常见什么用途

答：

- 代码补全、单测生成、代码解释、SQL 生成、脚本辅助、变更总结、代码审查建议。
- 如果再配合工具和工作流，就能进一步做自动修复、批量重构、研发助手。
- 但要注意：代码模型输出天然有执行风险，所以更需要沙箱、审计和权限边界。

### 41. 结构化输出为什么是 AI 应用的重要能力

答：

- 因为业务系统最终要落数据库、调接口、触发流程，不能长期靠正则去拆自然语言。
- 结构化输出能把模型返回限制为 JSON 或特定 schema，更容易映射到 Java 对象。
- 这通常比“让模型自己写一段解释”更适合生产系统。

### 42. Tool Calling 到底是模型能力还是应用能力

答：

- 更准确地说，它是“模型提出调用意图，应用真正执行工具”的协作能力。
- 模型只能给出工具名和参数，真正访问数据库、发邮件、调流程的是应用层。
- 这点非常重要，因为它直接关系到安全边界和系统设计责任归属。

### 43. 内容安全和审核为什么不能只靠模型自觉

答：

- 因为模型并不是可靠的安全边界，它可能被诱导、绕过或在边界情况下表现不稳。
- 生产系统要把审核、权限、脱敏、人工复核、黑白名单作为外部治理能力。
- 面试时这样回答，会显得你知道“模型负责生成，系统负责兜底”。

## 五、项目表达与常见追问

### 44. 面试官问“你们为什么选这个模型”时，应该怎么答

答：

- 不要只说“效果好”，要从能力、成本、延迟、部署形态、合规和生态支持一起回答。
- 最稳妥的答法是：先说明候选模型集合，再讲评测维度，最后说最终取舍原因。
- 比如可以说：复杂任务用能力更强的模型，常规任务用低成本模型，并做路由和降级。

### 45. 如果面试官问“为什么不用自己训练大模型”

答：

- 可以直接说：绝大多数业务问题不需要自研基础模型，投入产出比不成立。
- 企业更常见的路径是模型选型、Prompt 工程、结构化输出、工具调用、工作流编排和局部微调。
- 这能体现你有现实工程观，而不是停留在论文视角。

### 46. 你怎么证明自己不是只会调 API

答：

- 你要主动讲 token 成本、采样参数、上下文预算、结构化输出、工具调用、流式输出、重试限流、监控告警这些工程细节。
- 如果再能说清本地模型、量化、模型路由、部署方式和评估体系，就已经明显超出“只会接接口”的层次。

### 47. 这一部分最容易犯的回答错误是什么

答：

- 把模型讲成数据库。
- 把 Prompt 工程讲成万能解法。
- 把长上下文讲成无限上下文。
- 把工具调用讲成模型自己能执行代码。
- 把量化、微调、蒸馏混成一个概念。

### 48. 这一部分最后该怎么总结

答：

- 大模型基础部分的核心，不是背术语，而是理解每个概念对应的工程后果。
- 你至少要能把“模型能力边界、成本结构、性能瓶颈、适配方式、服务化形态”这五件事说清。
- 只要这五件事稳，后面的 Java 集成、Agent、评估、安全、运维才有根基。


### 49. 什么时候需要对用户问题做改写（Query Rewrite）？

答：

- 问题改写不是默认全开，而是**按需触发**，因为每次改写都是一次额外 LLM 调用，有成本和延迟。
- 常见必须改写的信号：
  1. 多轮对话里出现指代词（它、这个、那个、上次、上面）。
  2. 问题过短（如“多少钱？”“怎么用？”），缺少可检索实体。
  3. 首轮以外、语义不自包含，离开历史就无法检索。
- 常见可以不改写的情况：首轮且问题完整；闲聊/元问题（不必走检索）；已能稳定命中的短 FAQ。
- 工程上更稳的做法是：配置开关（OFF/ON/AUTO）+ 规则（长度/指代）+ 可选小模型判定；检索分数过低时再触发二次改写补检。
- 面试金句：**改写只在能显著提升检索质量时触发，否则就是白花钱。**

### 50. 意图分类器在 AI 应用里怎么做？该抄哪类方案？

答：

意图分类解决的是“这个问题该走哪条链路”，常见四类做法：

| 方案 | 做法 | 延迟/成本 | 适合场景 |
| :--- | :--- | :--- | :--- |
| LLM 选择题路由 | 把候选意图描述塞给模型让它选 | 高 | 意图灵活、准确率优先 |
| 向量语义路由 | 为每个意图准备示例句，算相似度 | 很低 | 内部系统、预算紧、要快 |
| 可视化 Prompt 节点 | 意图做成可配置节点（类似 Dify） | 中 | SaaS / 业务方可配置 |
| 漏斗混合 | 规则 → 轻量分类模型 → LLM 兜底 | 综合最优 | 高并发生产 |

Java 落地建议：

1. 先做二分类：知识问答 vs 闲聊/拒答，不要一上来十几种意图。
2. 有 Embedding 就优先做语义路由，延迟通常可压到几十毫秒级。
3. 需要灵活配置时，把意图配置存库，用便宜小模型做分类节点。
4. Agent/工具场景可直接用 Function Calling 让模型选工具，少写硬编码分类。

## 六、补充高频题（原文档遗漏）

### 51. Few-shot、Zero-shot、Chain-of-Thought 分别是什么，工程上怎么用？

答：

- Zero-shot：只给任务说明，不给示例，适合简单、格式约束强的任务。
- Few-shot：给少量正例/反例，适合稳固风格、格式、边界行为。
- Chain-of-Thought（CoT）：引导模型分步推理，适合复杂分析；代价是更慢、更贵，且推理过程可能含敏感信息，生产上要注意是否对外暴露。
- 工程取舍：能用结构化输出和工具解决的，不要默认上长 CoT；需要可审计时，可把“思考过程”与“最终答案”分字段返回。

### 52. 什么是 MoE（混合专家）模型？对应用侧意味着什么？

答：

- MoE 不是每次激活全部参数，而是按 token/请求路由到部分专家子网络。
- 好处通常是：同等总参数下推理激活参数更少，性价比更好。
- 应用侧要注意：厂商报价和实测吞吐可能与“参数量直觉”不一致；冷门专家路径可能不稳定；选型仍以任务评测为准，不要只看参数规模宣传。

### 53. 什么是 Speculative Decoding（投机解码）？

答：

- 用小草稿模型快速生成候选 token，再由大模型并行验证，从而加速解码。
- 它主要优化 TPS / 总生成时延，对 TTFT 帮助相对有限。
- 面试里能说到“草稿-验证”就够，细节留给推理服务团队；应用工程师更关心是否开启以及延迟收益是否稳定。

### 54. PagedAttention / 连续批处理为什么常和 vLLM 一起被提到？

答：

- PagedAttention 用类似操作系统分页的思路管理 KV Cache，减少显存碎片，提高并发承载。
- Continuous Batching 允许解码过程中动态加入新请求，提升 GPU 利用率。
- 对 Java 应用侧的意义是：本地/私有化高并发推理时，选对推理引擎往往比盲目加机器更划算。

### 55. temperature 和 top_p 能不能一起猛调？有没有更稳的实践？

答：

- 可以同时设置，但不建议同时大幅调高；两者都会扩大采样空间，叠加后结果更飘。
- 实践建议：事实抽取 / 工具参数生成，temperature 接近 0；创意写作再放开。
- 生产上最好把采样参数做成按任务类型的配置，而不是全局一个默认值。

### 56. 什么是模型网关（Model Gateway）？为什么企业常单独做一层？

答：

- 模型网关是统一的模型访问入口，负责鉴权、路由、限流、配额、审计、Fallback、协议适配。
- 好处：业务服务不直接绑死各家 SDK；成本可按租户/应用结算；故障可统一降级。
- Java 体系里常见形态是独立 Spring Boot 服务 + 统一 Client SDK。

### 57. 语义缓存（Semantic Cache）是什么？和普通 KV 缓存有什么区别？

答：

- 普通缓存按精确 key（如 prompt hash）命中；语义缓存按查询向量相似度命中近似问题。
- 适合高重复、答案稳定、时效性不强的 FAQ / 制度问答。
- 风险：相似但不该复用的问题被误命中；权限不同的答案串用。所以必须带租户/权限维度，并设相似度阈值与 TTL。

### 58. 对齐（Alignment）和应用层 Guardrail 是什么关系？

答：

- 对齐是训练阶段让模型更符合人类偏好与安全边界。
- Guardrail 是应用/平台层的输入输出策略：敏感词、PII 脱敏、主题拒答、工具白名单、输出 schema。
- 面试正确表达：**对齐降低坏行为概率，Guardrail 提供确定性兜底；两者都要，不能互相替代。**

### 59. 为什么说“上下文窗口变大”不等于“有效上下文变强”？

答：

- 窗口只是容量上限；中间迷失、注意力稀释、噪声片段过多都会让有效利用率下降。
- 所以长窗口模型普及后，仍要做检索、摘要、重排和上下文预算；只是“小知识库整库塞入”的可行性提高了。

### 60. 开源模型私有化部署时，应用工程师最该问推理团队哪 5 个问题？

答：

1. 目标并发和 P95 TTFT / TPS 是多少？
2. 量化精度与效果回退是否可接受？
3. 是否支持连续批处理、前缀缓存、工具调用？
4. 冷启动与滚动升级怎么做？
5. 失败码、超时、限流信号如何暴露给上游 Java 服务？
