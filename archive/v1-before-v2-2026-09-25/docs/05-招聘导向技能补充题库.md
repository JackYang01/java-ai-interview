# 招聘导向技能补充题库

## 1. 这份补充题库解决什么问题

这一份不是重复讲大模型基础，也不是重复讲 RAG 主线，而是专门补招聘 JD 里高频出现、但很多候选人容易准备不够的内容。

目标很明确：

- 让你更像一个真正能交付 Java AI 应用的人。
- 让你的回答更贴近真实岗位要求，而不是停留在通用概念层。

## 2. AI 编程工具链与人机协作开发

### 1. 为什么 AI 编程工具会进入 AI 应用岗位 JD

因为企业现在不仅要求你会做 AI 功能，还要求你能更快地交付 AI 功能。Cursor、Claude Code、Codex 这类工具的价值，不只是代码补全，而是把需求分析、样板代码生成、单元测试编写、重构、排错这些环节整体提速。

招聘里出现这些工具，说明公司已经把“AI 提升研发效能”当成岗位能力的一部分。

### 2. 面试官问你会不会用 Cursor 或 Claude Code，怎么回答更稳

最稳的答法不是说“我用过”，而是按流程讲：

1. 我会先把需求切成明确子任务。
2. 用 AI 工具生成初版样板代码和测试骨架。
3. 对关键逻辑、接口边界、异常处理、权限和安全点做人工审查。
4. 对生成结果做本地验证、单测、集成测试和代码 review。

这样回答的重点是：你把 AI 工具当提效助手，而不是把它当自动写完一切的黑盒。

### 3. 人机协作开发思维到底在说什么

它不是一句空话，核心是三件事：

1. 会把问题描述得足够清晰，让 AI 真正理解上下文。
2. 会判断哪些任务适合交给 AI，哪些任务必须人工把关。
3. 会把 AI 生成结果纳入正式工程流程，而不是直接复制上线。

面试里可以直接讲：AI 擅长提速，工程师负责边界、取舍和最终质量。

### 4. AI 编程工具最适合帮你做什么

最适合的几类任务是：

1. 生成 CRUD、DTO、Mapper、测试样板。
2. 根据接口定义补全前后端联调代码。
3. 帮你重构重复逻辑。
4. 根据错误日志做第一轮定位。
5. 帮你解释陌生代码、生成文档和测试用例。

这些任务的共同特点是上下文明确、校验成本可控、收益高。

### 5. AI 编程工具最不适合直接替你做什么

最不适合直接放手的部分包括：

1. 核心业务规则。
2. 权限与安全逻辑。
3. 性能瓶颈处理。
4. 复杂分布式事务和幂等设计。
5. 涉及真实合规约束的实现。

原因很简单：这些问题不是“能不能写出代码”，而是“能不能做对架构取舍”。

### 6. 面试里怎么证明你不是只会用 AI 写代码

你可以用一句话收束：

我会用 AI 工具提高编码效率，但系统边界、接口契约、性能取舍、安全审计和上线质量这些事，最终还是由工程师负责。

这句话很重要，因为它直接体现你的工程成熟度。

## 3. Java 硬核工程能力在 AI 应用里的表达

### 7. 为什么 AI 应用岗位还要求 JVM、GC 和 SQL 调优

因为 AI 应用的瓶颈从来不只在模型本身，还经常出现在 Java 服务层、数据库层、缓存层和消息层。

如果一个 AI 接口要承接流式输出、多轮会话、工具调用、异步任务和高并发访问，那 JVM、GC、连接池、SQL、Redis 命中率这些问题照样会成为线上瓶颈。

### 8. Java AI 应用里最常见的性能瓶颈有哪些

常见瓶颈通常有：

1. 模型响应慢，导致整体 RT 被拉长。
2. 流式输出时连接占用时间过长。
3. 多轮会话导致上下文拼接成本升高。
4. 工具调用串行太多，链路变长。
5. 数据库和缓存没有做好分层，热点请求反复击穿。

所以招聘里才会同时要求 AI 能力和传统性能优化能力。

### 9. Redis 在 AI 应用里通常怎么用

Redis 在 AI 应用里最常见的作用有：

1. 缓存热点回答或中间结果。
2. 缓存会话状态和短期上下文。
3. 做限流、幂等键、分布式锁。
4. 做异步任务状态跟踪。

面试里不要只说“Redis 提高性能”，而要说清它在 AI 应用链路里具体缓存什么。

### 10. 为什么消息队列在 AI 应用里很常见

因为很多 AI 任务都不适合同步阻塞完成。

比如文档解析、批量向量化、长文本摘要、离线评测、模型回放、复杂 Agent 执行，这些更适合放到消息队列和异步消费者里处理。

所以 RabbitMQ、Kafka 在 AI 应用岗位里依然是高频要求。

### 11. Dubbo 或 gRPC 在 AI 应用里有什么价值

如果 AI 能力不是直接嵌在单体系统里，而是被拆成独立服务，比如模型网关、检索服务、评测服务、工具服务，那么 RPC 就很自然。

Dubbo 更贴近 Java 微服务生态，gRPC 更适合高性能跨语言调用。面试时能讲清“为什么要把 AI 服务能力抽成独立服务”，就已经很加分。

### 12. 微服务在 AI 应用里应该怎么拆

比较稳的拆法通常是按能力边界来：

1. 模型接入层。
2. 会话与编排层。
3. 检索与知识层。
4. 工具与外部系统接入层。
5. 评测与观测层。

重点不是拆得多细，而是每层职责清楚，故障和扩容边界清楚。

### 13. 面试官问“AI 应用为什么还需要高并发设计”，怎么答

因为 AI 应用不等于低并发后台任务。很多场景是面向真实用户实时交互的，例如智能客服、Copilot、企业问答、流程助手。

这类场景下，你要同时承受会话连接、流式输出、工具调用和数据库访问，高并发设计依然是刚需。

### 14. Java 后端硬实力怎么和 AI 经验合成一句更强的自我介绍

可以这样说：

我不是只会接大模型 API，我本质上还是做企业级后端工程的，只是把模型能力接进了成熟的 Java 系统里，所以我会同时关注模型效果、接口稳定性、缓存、异步、限流、观测和上线治理。

## 4. 全栈交付与前后端协同

### 15. 为什么不少 Java AI 应用岗位会要求 Vue 或 ElementUI

因为很多 AI 功能最终都要做成可交互界面，比如聊天窗口、引用展示、工作流配置台、Prompt 配置页、知识库管理页、评测后台。

企业不一定要求你是前端专家，但往往希望你至少能独立完成一个模块的前后端联调。

### 16. Java AI 应用里常见的前端交互难点有哪些

常见难点包括：

1. 流式输出展示。
2. 工具调用中间态展示。
3. 引用片段和来源展示。
4. 多轮会话状态同步。
5. 长任务执行过程中的轮询或推送反馈。

如果你能把这些说出来，面试官会更相信你真的做过产品级交付。

### 17. 做 AI 应用前后端联调时，接口设计要注意什么

最重要的是三点：

1. 明确同步接口和异步接口边界。
2. 明确流式事件格式。
3. 明确错误码、重试策略和中断恢复方式。

AI 应用接口如果没有状态语义，前端体验通常会很差。

### 18. SSE 和 WebSocket 在 AI 应用前端里怎么选

如果主要是服务端持续向前端推送模型输出，SSE 往往更简单。

如果需要双向频繁互动、状态控制更复杂，WebSocket 更灵活。

大多数聊天式 AI 页面，用 SSE 就已经够了；面试里这样答通常比较稳。

### 19. 为什么“能联调”在 AI 应用岗位里是加分项

因为 AI 功能的可用性很多时候不只取决于后端逻辑，还取决于前端是否正确处理流式输出、引用、工具状态、失败回退和用户输入体验。

会联调的人，往往更懂完整交付链路。

### 20. 面试里怎么讲你有全栈协同能力但又不冒充前端专家

可以这样说：

我的主战场还是 Java 后端，但我能独立完成 AI 功能模块的接口设计、流式交互联调、状态展示对接和基本前端问题排查，所以在小团队或快速试验阶段可以把交付链路拉通。

## 5. 上下文工程、MCP、技能库与编码优先 Agent 架构

### 21. Prompt 工程和上下文工程有什么区别

Prompt 工程更偏“怎么写一句好提示词”，上下文工程更偏“怎么把正确的信息、工具、历史、状态和约束组织给模型”。

越到复杂业务场景，真正决定效果的通常不是单句 Prompt，而是上下文组织方式。

### 22. 为什么招聘里开始出现上下文工程

因为企业已经发现，很多 AI 应用效果不稳定，问题不在模型不够强，而在上下文给得不对。

比如历史消息太乱、工具说明不清、业务规则没注入、检索片段组织差，这些本质上都属于上下文工程问题。

### 23. MCP 在招聘语境里应该怎么讲

最稳的说法是：

MCP 是把模型应用和外部工具、数据源、运行环境连接起来的标准协议层，它的价值在于减少每个工具都单独适配的重复工作，让工具生态更标准化。

如果再进一步，可以补一句：MCP 让工具接入从硬编码逐步走向协议化。

### 24. 技能库开发是什么意思

技能库本质上是在做工具能力和任务能力的模块化封装。

你可以把它理解成：

- 给 Agent 准备一组可复用能力。
- 每个能力有输入、输出、权限边界和失败处理。
- 不同业务场景通过组合这些能力完成复杂任务。

这其实和传统软件工程里的服务封装思想非常接近。

### 25. 什么叫编码优先智能体架构

它强调的是：

不要把 Agent 当成完全靠自然语言自由发挥的黑盒，而要用代码把流程、状态、工具、边界和约束显式组织起来。

这种方式更适合企业级应用，因为更稳定、更可测、更容易治理。

### 26. 为什么函数调用和工具设计会成为高频要求

因为企业真正需要的不是一个只会聊天的模型，而是一个能调用搜索、数据库、审批、报表、工单、通知等真实工具的应用系统。

一旦进入这个层面，函数调用设计、参数校验、权限控制、失败恢复就都成了工程重点。

### 27. 面试里怎么把这些新词讲得不虚

建议统一收束成一句：

我理解这些词本质上都在解决同一个问题，就是如何把模型能力稳定地接到真实系统里，而不是只做一次自由问答。

这句话能把新概念迅速拉回工程主线。

## 6. 云原生、平台化与评测工程

### 28. 为什么 AI 平台岗位会要求 Docker 和 Kubernetes

因为 AI 应用很少只是一段代码，它通常涉及模型服务、网关、检索、缓存、异步任务、观测和后台管理。

一旦服务变多，就会自然走向容器化和编排。Kubernetes 在这里解决的是部署、扩缩容、隔离、滚动发布和资源治理问题。

### 29. 多模型、多智能体平台为什么难做

难点不在于“多接几个 SDK”，而在于：

1. 模型能力差异大。
2. 成本和性能差异大。
3. 流式能力、结构化能力、工具能力支持不一致。
4. 不同 Agent 的状态管理和任务调度复杂。

所以平台化岗位通常会更看重抽象能力和治理能力。

### 30. AI 平台里的成本治理应该怎么讲

最常见的成本治理手段包括：

1. 模型分级路由。
2. 缓存与结果复用。
3. 限流和配额。
4. 长任务异步化。
5. 对低价值请求做降级。
6. 通过评测避免无效优化和无效切模型。

面试里如果只说“控制 token 成本”，维度还是太窄。

### 31. 自动化评测体系为什么会进入 JD

因为企业已经从“做出来能跑”进入“要持续优化效果”的阶段了。

没有评测体系，模型版本变更、Prompt 调整、RAG 优化、工具改造都很难判断到底是进步还是退步。

### 32. 自动化评测体系通常评什么

常见指标有：

1. 准确率。
2. 相关性。
3. 幻觉率。
4. 工具调用成功率。
5. 响应延迟。
6. 用户反馈和业务转化指标。

如果是 RAG 场景，还会看召回质量、引用质量和答案可追溯性。

### 33. Fine-tune 和 RAG 在招聘里应该怎么讲取舍

稳妥答法是：

如果问题主要在知识更新、可追溯性和业务知识外挂，优先 RAG；如果问题主要在输出风格、任务习惯和行为模式，才考虑微调。很多企业会先做 Prompt 加 RAG，再决定要不要上 Fine-tune。

### 34. 面试收尾时，怎么把平台化、工程化和业务化统一起来

可以用一句话收束：

我理解 Java AI 应用岗位的核心，不是单点模型调用，而是把模型、工具、业务系统和工程治理体系整合成一个稳定、可评估、可演进的生产能力。

如果这句话你能自然说出来，面试官通常会觉得你的视角已经明显超过只会做 Demo 的层次。

## 7. 消息队列与 AI 应用架构决策

### 35. 为什么不能直接往大模型里打请求，一定要用消息队列吗

MQ 并不是 100% 绝对必用的，但"直接往大模型里打请求"在真正的生产级、高并发、核心业务链路中，是架构红线，是绝对不允许的。

要不要用 MQ，完全取决于业务场景和并发量级。核心判断标准是：大模型 API 是一种极其昂贵、极其缓慢且极其脆弱的外部资源，对待这种资源，传统的直连调用是野蛮的；通过 MQ 或队列机制进行排队、限流、异步、解耦，才是企业级生产环境应有的做法。

### 36. 什么情况下可以不用 MQ，直接调用大模型

如果项目属于以下 3 种情况，完全可以不用 Kafka/RocketMQ，直接通过 HTTP 客户端（如 WebClient/RestClient）调用大模型 API：

1. **企业内部工具 / 低并发 B 端后台**：比如公司内部的合同审查助手、代码 Review 机器人，同时在线使用的员工不超过几十个人。
2. **MVP（最小可行性产品）验证阶段**：项目刚起步，核心目标是快速验证大模型的效果（Prompt 调优），还没到大规模推广阶段。
3. **有强大的 API 网关兜底**：系统前置了极其完善的 API 网关（如 APISIX、Kong）或限流组件（如 Alibaba Sentinel），在网关层就做好了请求排队、令牌桶限流和超时熔断，后端服务只负责透传。

在这些场景下，不用 MQ 是为了降本增效，避免过度设计。

### 37. 不用 MQ 直接调用大模型会面临哪些生产级灾难

如果不加 MQ 直接把请求打给大模型，会面临以下 4 个生产级灾难：

**线程池雪崩（最致命）**：传统 HTTP 请求耗时 50ms，大模型请求耗时 5～30 秒。Tomcat 的默认 200 个线程会被大模型的长连接瞬间占满，导致整个 Java 服务假死。有人会说用 Java 21 虚拟线程（Virtual Threads）来解决，但虚拟线程能解决"线程耗尽"问题，解决不了大模型 API 的限流问题。

**大模型 API 的 429 限流（最烧钱）**：所有大模型厂商都有严格的 RPM（每分钟请求数）和 TPM（每分钟 Token 数）限制。不用 MQ 做蓄水池和定速消费，突发流量瞬间涌入大量请求，大模型会返回 429 Too Many Requests，导致大量用户请求直接失败。MQ 是天然的排队系统，无论前端来多少请求，先扔进 MQ，后端消费者根据大模型的限流阈值匀速平滑地调用，保证成功率。

**用户取消请求但钱已扣（算力浪费）**：用户等不及关闭网页后，后端线程可能还在等待大模型返回，Token 费用已被扣除但结果丢弃。在 AI 应用中 Token 就是真金白银，这种浪费在财务上无法接受。

**大模型宕机导致系统被拖死（强耦合）**：大模型服务商偶尔会出现网络抖动或宕机。引入 MQ 后，AI 模块和核心业务模块物理隔离，大模型宕机时消息堆积，但主业务系统不受影响，恢复后继续处理堆积消息。

### 38. 有哪些轻量级替代方案可以代替 Kafka/RocketMQ

有些团队觉得 Kafka/RocketMQ 太重了（需要独立部署集群、运维成本高），但又不想直接打大模型，可以采用以下轻量级替代方案：

**Redis Stream / Redis List（中小企业最爱）**：用 Redis 的 List（LPUSH/BRPOP）或 Redis Stream 代替 Kafka。AI 项目基本必用 Redis（做缓存、多轮对话记忆、流式推送），顺手做任务队列省去维护 Kafka 的成本。缺点是 Redis 是内存数据库，消息堆积能力远不如 Kafka/RocketMQ，大模型宕机时间过长可能撑爆内存。

**JVM 内存队列 + 信号量限流（单机极简版）**：使用 Java 自带的 LinkedBlockingQueue 或 Semaphore 在内存中做排队和限流。零外部依赖，但存在单点故障风险——服务器重启或宕机时排队中的请求全部丢失，只适合允许少量丢失的非核心场景。

**Spring Retry + Resilience4j（重试与熔断框架）**：在调用大模型的 HTTP 客户端上加上重试、退避（Backoff）和熔断机制。但这只能解决偶尔失败的问题，解决不了突发高并发的排队问题。

### 39. 生产环境下消息队列的架构决策树是什么

总结为三条决策路径：

1. **内部小工具 / 验证性 Demo / 日活不到 1000**：不用 MQ，直接 HTTP 调用大模型，加 Resilience4j 做超时和重试，用 Java 21 虚拟线程防阻塞即可。

2. **日活过万的 C 端产品 / 核心 SaaS 业务 / 对成功率要求极高**：必须上 MQ（Kafka / RocketMQ / RabbitMQ），用 MQ 做任务派发、削峰填谷、死信重试。

3. **中小团队，想兼顾高可用和低运维成本**：采用 Redis 全家桶——用 Redis List/Stream 做任务排队（代替 MQ），Redis Pub/Sub 做流式输出，Redis Hash 做多轮对话记忆。这是性价比最高、国内用得极多的轻量级企业级架构。

## 8. 知识库架构与文档分块（Chunking & Parsing）

### 40. 如果 WBS 表格跨页了，或者表头有复杂的合并单元格，解析和分块策略怎么保证语义不丢失

跨页表格是 PDF 解析的噩梦，合并单元格会导致解析出来的行列对不齐。解决方案：引入视觉大模型（VLM）或高级文档解析工具（如 Marker、MinerU）。如果纯靠代码，需要在解析层做跨页表格合并逻辑（判断上一页末尾和下一页开头的线条特征），对于合并单元格，在转 Markdown 时进行单元格向下/向右填充操作，确保每一行数据都有完整的表头对应。

这道题考察的是对真实脏数据的处理经验，而不是只跑过完美数据集。

### 41. Chunk Size（分块大小）设多大合适，设大了和设小了分别有什么致命影响

设太小（如 100 字）：语义碎片化，Embedding 向量无法表达完整上下文，且检索出来的片段 LLM 看不懂（缺乏前置条件）。

设太大（如 2000 字）：超出了多数 Embedding 模型（如 BGE 通常是 512 token）的最佳感受野，导致语义稀释（Lost in the middle）；且占用 LLM 宝贵的 Context Window，增加 Token 成本。

确定方法：基于业务文档的平均段落长度，结合肘部法则做实验。通常设置在 300～500 Token，并保留 10%～20% 的 Overlap（重叠）。这道题考察的是对 Embedding 模型特性和 LLM 上下文窗口的理解。

### 42. 长篇 PRD 切成小块后，用户问题需要综合多块内容，怎么解决上下文碎片化问题

这是经典的"局部与全局"矛盾。采用 Small-to-Big（父子文档/自动合并）策略。入库时，将文档切成大 Chunk（Parent，如 1000 字）和小 Chunk（Child，如 200 字）。向量库只存小 Chunk 的向量用于高精度检索。当召回某个小 Chunk 时，系统通过 parent_id 去数据库（或 Milvus 的标量查询）把对应的大 Chunk 甚至前后相邻的 Chunk 一起取出来，喂给 LLM。

这道题考察的是高级 RAG 架构设计（如 Parent-Child 策略）。

### 43. PRD 文档里有很多业务流程图或架构图，纯文本解析会丢失这些核心信息，怎么处理多模态内容

目前的务实方案是：在解析阶段，把图片裁剪出来，调用多模态大模型（如 Qwen-VL 或 GPT-4o）生成一段图片描述文本（Caption），然后将这段描述文本作为普通的 Chunk 插入到原文档对应的位置，并打上 doc_type: image_caption 的 Metadata 标签，随正文一起入库和检索。

这道题考察的是对多模态 RAG 的前沿认知。

## 9. RAG 检索链路优化（Retrieval & Rerank）

### 44. 混合检索中，向量检索和 BM25 的结果融合时，RRF 算法里的常数 k 怎么确定

RRF 公式中的 k（通常默认 60）用于控制排名靠前和靠后文档的分数衰减梯度。k 越大，排名对分数的影响越平缓。如果业务极度依赖精确匹配（如外包项目代号、特定 API 名称），可以：

1. 放弃纯 RRF，改用加权线性组合（Linear Combination），手动调高 BM25 的权重（如向量 0.3 + BM25 0.7）。
2. 在 BM25 侧引入同义词词典或提升特定字段（如 project_code）的权重。

这道题考察的是对检索算法底层参数的调优经验。

### 45. 有没有遇到过 Rerank 模型把原本正确的文档排到后面，甚至导致召回率下降的 Bad Case

遇到过。比如用户搜"微服务网关配置"，向量检索召回了包含"Zuul 路由规则"的文档（语义相近），但 Rerank 模型（可能是通用领域训练的）认为字面不匹配，把分数打得很低。

排查方式：通过打印检索日志（Tracing）发现。解决方式：

1. 更换在代码/IT 领域微调过的 Rerank 模型（如 bge-reranker-large）。
2. 在 Rerank 前加一层硬规则保护——如果 BM25 命中核心专有名词，强制保底进入 Top-K，不被 Rerank 刷掉。

这道题考察的是真实踩坑经验——Rerank 不是万能药。

### 46. 如何做 Prompt 优化来控制大模型幻觉，如果知识库里真的没有答案，系统怎么表现

**Prompt 约束**：使用强烈的 System Prompt——"你是一个严谨的助手。必须且只能基于提供的 context 回答。如果 context 中没有相关信息，请明确回答'当前项目知识库中未找到相关记录'，严禁使用你的内部知识编造。"

**工程兜底**：在检索后加一个相关性阈值判断。如果 Rerank 返回的 Top-1 分数低于 0.5（说明召回的文档跟问题根本不搭），直接拦截，不调用 LLM，前端直接返回"未找到相关知识"。

这道题考察的是 Prompt Engineering 和幻觉控制的工程落地能力。

### 47. 用户要求总结某项目最近几个月的周报要点，这种长文本摘要 RAG 直接做效果很差，怎么解决

普通的 RAG（Stuff 模式，把 Top-K 塞进一个 Prompt）搞不定长文本总结。需要改用 Map-Reduce 策略：

1. **Map**：把多份周报（或拆分后的多个 Chunk）分别发给 LLM，让其提取单份周报的核心要点、风险、进度。
2. **Reduce**：把这些提取出的要点汇总，再发给 LLM 做一次全局的归纳和总结。

虽然耗时和 Token 成本增加，但摘要质量大幅提升。这道题考察的是对 Map-Reduce 或 Refine 等高级 LLM 链路的理解。

## 10. 多轮对话与原文溯源（Conversation & Tracing）

### 48. Query Rewrite（查询重写）如果 LLM 改写错了，导致检索跑偏，怎么防范

不能盲信 LLM 的重写。策略：

1. **保留双路检索**：用重写后的 Query 和用户原始 Query 同时去向量库检索，合并结果。
2. **约束重写格式**：在 Rewrite Prompt 中要求 LLM 输出 JSON，包含 rewritten_query 和 confidence_score（置信度）。如果置信度低，降级使用原始 Query。

这道题考察的是对 LLM 链路中"错误级联"的防御设计。

### 49. 多轮对话中 Redis 里的历史记录越来越长，除了滑动窗口和摘要，还有什么省 Token 的高级玩法

引入语义缓存（Semantic Cache）或实体记忆（Entity Memory）。

实体记忆的做法：不让 LLM 总结对话，而是让 LLM 从对话中抽取关键实体（如：项目=A，当前阶段=UAT，核心风险=人员流失），以 JSON 形式存在 Redis 里。下次提问时，只把这段 JSON 作为 System Context 传入，极其省 Token。

这道题考察的是大模型应用的成本优化意识。

### 50. 原文溯源（Citation）功能中，LLM 在回答时张冠李戴，引用的 Chunk 是错的或编造引用标记，怎么解决

LLM 确实会乱编引用标记（如 `[引用: doc_999]`）。解决方案：不依赖 LLM 自己生成引用标记，而是在 Java 后端做后处理（Post-processing）。

做法：LLM 只负责基于给定的带 ID 的 Context 生成回答。后端拿到回答后，通过计算回答文本与各个 Context Chunk 的文本相似度（如 ROUGE 或简单的 N-gram 匹配），由后端代码自动在回答中插入正确的溯源超链接。

这道题考察的是对 LLM 输出格式控制和后处理的工程能力。

### 51. 用户在前端点击溯源锚点后，弹出的原始文档段落非常长，用户体验很差，怎么优化

1. 弹窗展示时，默认高亮（Highlight）命中的那个 Chunk，并将页面自动滚动（Scroll-to）到该位置。
2. 提供"上下文展开"按钮，允许用户查看该 Chunk 前后各 200 字的内容，而不是直接扔给用户一个 50 页的 PDF。

这道题考察的是 AI 应用的前后端交互体验设计。

## 11. 异步入库与 Metadata 构建（Ingestion & Metadata）

### 52. 自动提取 Metadata（如项目阶段、业务模块）时，小模型抽取的标签和人工打的标签不一致，怎么优化

1. **Few-shot Prompting**：在抽取 Prompt 中提供 3～5 个公司历史文档的标准打标示例。
2. **限制输出空间**：不让 LLM 自由发挥，在 Prompt 中明确给出枚举值（如"项目阶段只能是：启动、规划、执行、监控、收尾"），并要求输出严格的 JSON 格式。
3. **Human-in-the-loop（人工介入）**：入库后状态为"待确认"，交付经理在前端可以一键修改错误的标签，修改后的数据定期导出，用于微调（Fine-tune）本地的小模型。

这道题考察的是数据飞轮和模型微调/提示词优化。

### 53. 如果一份 PRD 文档只是修改了其中两个章节，重新上传时怎么做增量更新

全量删除重插（Delete by doc_id → Insert）会导致该文档在更新期间短暂不可搜，且重新生成全量 Embedding 浪费算力和 API 费用。

优化方案：在解析层做文档 Diff（差异对比）。对比新旧文档的 Chunk，计算出新增、删除和修改的 Chunk。在向量库中，只针对这些变化的 Chunk 执行 Delete 和 Upsert 操作。

这道题考察的是向量数据库的数据一致性和更新策略。

### 54. 文档入库是长耗时任务，如果解析到一半 Worker 宕机或 Embedding API 超时，怎么保证数据不丢且不重复

1. **消息确认机制**：RabbitMQ 使用手动 ACK。只有当向量库写入成功并更新了 MySQL 状态后，才发送 ACK。如果 Worker 宕机，消息重回队列。
2. **幂等性设计**：每个 Chunk 的 ID 采用 doc_id + chunk_index 的哈希值。即使消息被重复消费，向量库执行 Upsert（按主键覆盖）也不会产生重复数据。
3. **断点续传**：记录解析进度，如果 Embedding API 批量调用失败，只重试失败的那一批 Chunk。

这道题考察的是分布式系统的可靠性设计（消息队列与幂等性）。

### 55. 知识库里有很多历史废弃文档，这些文档会严重干扰 RAG 检索，怎么处理

不能只靠物理删除。

1. **Metadata 标记**：入库时识别版本号，打上 is_latest: true/false 标签。检索时默认加上 is_latest == true 的过滤条件。
2. **时间衰减权重**：在 RRF 融合或 Rerank 阶段，引入时间衰减因子（Time Decay），越老的文档得分权重越低。

这道题考察的是知识库的生命周期管理（Data Governance）。

## 12. 项目级权限隔离与系统架构（Security & Architecture）

### 56. 如果用户 A 提问时 Filter 表达式拼接错误，导致搜出 B 项目的数据，这种越权在架构上怎么兜底

不能只靠向量库层的 Filter。必须做双重校验：

1. **网关/拦截器层**：在 Spring Boot 的 Interceptor 层，校验当前用户是否有权限访问他指定的 project_id。
2. **结果后置过滤（兜底）**：向量库返回 Top-K 结果后，在 Java 内存中再遍历一次，检查每个 Chunk 的 owner_id 或 project_id 是否真的属于当前用户。如果发现越权数据，直接丢弃并触发安全告警。

这道题考察的是安全防御的"纵深防御（Defense in Depth）"思想。

### 57. 向量数据库在做带复杂 Filter（多个 AND/OR 组合）的检索时，性能下降严重，怎么排查和优化

排查：查看向量库的 Query Node 日志，看是标量过滤耗时还是向量 ANN 搜索耗时。

优化：

1. 确保参与 Filter 的字段（如 project_id、doc_type）都建立了标量索引（如 INVERTED 索引）。
2. 尽量避免在 Filter 中使用复杂的模糊匹配（LIKE）或大范围的 IN 查询。
3. 将高频过滤字段（如 project_id）设置为 Partition Key，将过滤转化为物理分区裁剪。

这道题考察的是对向量数据库底层索引机制的理解。

### 58. 如何科学地评估 RAG 系统好不好用，有哪些评估指标

不能只凭感觉。主要关注三个核心指标（参考 RAGAS 框架）：

1. **Context Relevance（上下文相关性）**：检索出来的 Chunk 是否真的和用户问题相关？评估检索链路。
2. **Faithfulness（忠实度）**：LLM 生成的答案是否完全基于提供的 Context，有没有幻觉？评估生成链路。
3. **Answer Relevance（答案相关性）**：最终答案是否直接回答了用户的问题？

落地方式：构建一个包含 100 个"问题-标准答案-标准引用文档"的 Golden Dataset（黄金测试集），每次改动 Prompt 或分块策略后，跑自动化脚本计算这些得分。

这道题考察的是 RAG 评估体系（如 RAGAS 框架），是高级 AI 工程师的必修课。

### 59. 如果大模型 API 突然宕机或响应延迟飙升到 10 秒以上，系统有什么降级或容错策略

1. **多模型路由（Fallback）**：配置主备模型（如主用通义千问，备用文心一言或本地部署的 Qwen-7B）。通过 LangChain4j 的 Fallback 机制，主模型超时自动切换。
2. **语义缓存（Semantic Cache）**：对于高频问题（如"公司报销流程"），将问题和答案的向量存入 Redis。下次有相似问题（余弦相似度 > 0.95），直接返回缓存答案，根本不请求 LLM。
3. **前端交互降级**：如果流式输出（SSE）中断，前端提示"AI 助手正忙，正在为您检索原始文档..."，并直接展示检索到的 Top-3 原始文档片段，保证用户至少能拿到资料。

这道题考察的是 AI 应用的高可用设计——LLM 往往是最不可靠的组件。

## 13. 补充高频题（原文档遗漏）

### 60. Semantic Kernel 在招聘里出现时，你怎么讲才不虚？

答：

- 它是微软系的 AI 编排 SDK，核心也是 Prompt、Planner、Plugin/Function、Memory。
- 对 Java 候选人不必假装深度用过 C#/.NET 版；重点讲清：你理解“技能/插件化工具 + 规划器 + 记忆”的平台抽象，并且能在 Spring AI / LangChain4j 里对应实现。
- 面试稳妥句：框架名词会变，平台能力抽象不会变。

### 61. 等保 / 数据合规场景下，AI 应用面试常问什么？

答：

1. 敏感数据能不能出域（是否必须本地/专有云模型）。
2. 日志与评测样本如何脱敏、留存多久。
3. 权限、审计、操作留痕是否覆盖工具调用。
4. 知识库内容分级与跨境传输限制。
- 回答框架：数据分类分级 → 模型部署形态 → 传输加密 → 审计可追溯 → 最小化采集。

### 62. “编码优先 Agent / Skills”在 JD 里到底指什么？

答：

- 不是让模型随意写生产代码直接上线，而是把可复用能力沉淀为明确技能模块（函数、脚本、工作流节点），由 Agent 按需调用。
- 工程重点：技能契约（输入输出 schema）、权限、测试、版本发布。
- 和“纯 Prompt 堆功能”的区别是：能力可测试、可复用、可治理。

### 63. AI 全栈联调时，引用高亮和流式输出最容易踩什么坑？

答：

- 流式过程中引用 id 尚未齐备，前端过早渲染导致错位。
- SSE 断连后状态不同步，页面停在“生成中”。
- 引用锚点和原文偏移量在分块后失效。
- 稳妥做法：先推送文本 delta，完成后再推送 citations 事件；或边生成边推送已确认的引用。
