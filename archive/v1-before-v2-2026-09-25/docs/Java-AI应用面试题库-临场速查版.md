## 二、一张图记住整个知识体系

把 Java AI 应用整体理解成两条主线：

**非 RAG 主线：**
```
模型能力 → Prompt 与结构化输出 → Tool Calling / MCP → Workflow / Agent
→ 状态管理与异步执行 → 评估 → 安全 → 观测 → 灰度上线
```

**RAG 主线：**
```
文档解析 → 清洗与切分 → Embedding 与索引 → 检索召回
→ 融合与重排 → Prompt 组装 → LLM 生成 → 评估与反馈闭环
```

> 只要你能把这两条链讲顺，面试基本不会散。

## 三、高频题一口气速答（20 题）

### 1. 为什么 Java 可以做 AI 应用

AI 训练主要在 Python，但 AI 应用落地是后端工程问题。Java 在企业系统集成、权限审计、任务调度、配置治理、监控运维这些方面更成熟。

### 2. Spring AI 和 LangChain4j 怎么选

如果更看重 Spring 生态统一治理，选 Spring AI；如果更看重 Java 侧快速开发体验，选 LangChain4j。核心不是谁更强，而是团队现有体系和治理诉求。

### 3. 为什么结构化输出重要

业务系统最终消费的是字段，不是自由文本。结构化输出更容易映射 Java 对象，也更容易校验和落库，是 AI 应用从 demo 到生产的关键一步。

### 4. Tool Calling 到底是什么

模型负责决定要不要调用工具和传什么参数，应用负责真正执行工具。它不是模型自己去访问系统，而是模型和应用协作完成动作。

### 5. Workflow 和 Agent 的区别

Workflow 是系统预定义流程，Agent 是把运行时部分决策权交给模型。流程固定、稳定性要求高时优先 Workflow；路径不确定、需要动态规划时才考虑 Agent。

### 6. 怎么控制 AI 成本

不要只看模型单价，要看整条链路。常见做法是模型路由、压缩上下文、限制输出、缓存、缩短工具链、对高成本流程做预算和配额。

### 7. 怎么做 AI 应用评估

至少分离线和在线两类。离线做版本回归，在线看真实业务表现。指标看任务成功率、结构化正确率、工具调用成功率、延迟、token 成本和用户反馈。

### 8. AI 应用安全最重要的点

Prompt Injection 不能只靠提示词防，真正要靠权限边界、工具白名单、输出校验、脱敏、审计和人工兜底一起做。

### 9. 大模型本质是什么

基于上下文预测下一个 token。因为参数规模和训练数据大，表现出通用能力，但不是数据库，不保证事实正确。

### 10. Transformer 关键是什么

自注意力和可并行扩展。

### 11. token 决定什么

成本、上下文和延迟，不是字数。

### 12. temperature 控制什么

控制发散度，结构化任务一般调低。

### 13. 幻觉的根因是什么

概率生成，不是数据库查询。

### 14. 微调不是默认解

先做 Prompt、结构化输出、工具和流程。

### 15. LoRA/PEFT 解决什么

低成本微调。

### 16. 量化解决什么

低成本推理。

### 17. 蒸馏是什么

大模型教小模型，适合控成本和低延迟。

### 18. 云模型 vs 本地模型

云模型适合快速试错，本地模型适合私有化和长期成本可控。

### 19. Agent 最怕什么

工具太多、没有终止条件、没有权限边界。

### 20. 生产系统一定要有什么

观测、灰度、回滚、幂等和审计。

## 四、RAG 10 分钟速记

### 一句话定义
RAG = 先检索外部知识，再让 LLM 基于检索结果回答。

### 一句话价值
让模型基于企业真实知识说话，而不是只靠参数记忆。

### 一句话难点
RAG 最大的问题通常不在生成，而在检索链路。

### 为什么企业更先做 RAG，不先做微调
企业大多数问题不是模型不会说，而是模型不知道企业自己的知识。RAG 更适合接私有知识、更新快、可追溯。

### 为什么 Chunk 很重要
Chunk 决定检索单位，也决定最终喂给模型的上下文粒度。切太小会碎，切太大噪声多。

### 为什么只做向量检索不够
向量检索擅长语义相似，但对错误码、编号、型号、缩写这类精确词项不稳定。

### 为什么需要 Rerank
第一阶段召回追求别漏掉，Rerank 是第二阶段精排，把最值得送给 LLM 的片段排上来。

### 多轮对话为什么难
用户后续经常只说代词或省略句，要做 query rewrite 把当前问题改写成独立问题再检索。

### 长上下文会不会替代 RAG
小知识库可以直接塞，大知识库仍然需要 RAG。长上下文有 lost in the middle 问题，也不利于权限过滤和增量更新。

### RAG 系统优化优先级
先补离线评测集 → 再加 query rewrite → 再接 rerank → 再补引用展示和链路埋点 → 最后再考虑 Self-RAG、GraphRAG 等前沿增强。

## 八、分模块口语化答法

### 8.1 模型基础高频题

#### 什么是大模型
> 大模型本质上是一个基于上下文预测下一个 token 的概率模型。因为训练数据量、参数量和算力规模都非常大，所以表现出泛化能力。大模型不是数据库，它擅长生成，不天然保证事实正确。

#### Transformer 为什么重要
> Transformer 的自注意力机制让模型能同时关注上下文中不同位置的信息，而且很适合并行训练，所以模型规模才能真正做大。没有 Transformer 这种可扩展架构，就不会有今天的大模型浪潮。

#### temperature、top_p 这些参数怎么理解
> 我把它们理解成生成时的随机性控制。temperature 越高，输出越发散；越低越稳定。top_p 是在高概率候选里截一个范围再采样。结构化的任务我一般把 temperature 调低，先保稳定。

#### 幻觉为什么会出现
> 模型本质上是在做概率生成，不是在查绝对真实的知识库。上下文不足、提示词不清、工具没接上、采样太发散，都可能导致幻觉。控制幻觉不能只靠一句 prompt，要结合结构化输出、工具、评估和护栏一起做。

#### 为什么很多项目不先微调模型
> 多数业务问题不是模型完全不会，而是任务约束不清、输出格式不稳、流程没设计好。真实项目里我会先做 Prompt、结构化输出、工具调用和工作流编排，只有在风格长期固定、数据质量够高时，才会考虑微调。

#### LoRA 和量化有什么区别
> LoRA 解决的是怎么更低成本地微调模型，让模型行为更贴近业务；量化解决的是怎么让模型更省显存、更省资源、更容易部署。一个偏训练适配，一个偏推理优化。

#### 云模型和本地模型怎么选
> 快速上线、先验证业务用云模型；数据敏感、成本长期可控要求高、要离线部署，用本地模型。项目里我倾向做一层 Provider 抽象，云和本地都能接。

### 8.2 Java 集成与工程化

#### 为什么 AI 应用可以用 Java 做
> 训练和底层推理很多在 Python 生态没错，但 AI 应用落地本质上是后端工程问题。企业里大量系统本来就是 Java，权限、审计、任务调度、消息队列、数据库、中间件、配置中心、灰度发布都已经成熟了。

#### Spring AI 和 LangChain4j 你怎么理解
> Spring AI 更贴近 Spring 生态治理，适合和 Actuator、Micrometer、配置体系一起用。LangChain4j 更偏 Java 开发体验，做 AI Service、对话、工具、记忆这些上手很快。怎么选主要看团队现有体系和治理诉求。

#### 为什么要做模型 Provider 抽象
> 项目里不太可能永远绑死一个模型供应商。抽象 Provider 之后，模型切换、灰度、回滚、路由都会简单很多。这决定后面系统有没有长期可维护性。

#### 结构化输出为什么重要
> 业务系统最终消费的是字段，不是一段自由文本。要落库、调用下游接口、触发审批流，JSON Schema 或 DTO 映射就比纯文本稳得多。AI 应用从 demo 走向生产，结构化输出是很关键的一步。

#### 流式输出为什么常用 SSE
> 聊天场景通常只需要服务端持续往前端推 token，SSE 比 WebSocket 更轻，也更容易和浏览器配合。用户体感最在意的是首 token 出得快不快。

#### 多轮对话的状态怎么管
> 我不会把所有历史原样一直拼进去，那样 token 成本会越来越高。我更倾向按窗口、摘要和关键状态来管理。真正要保留的是用户偏好、当前任务状态、必要的工具结果。

#### Tool Calling 到底是谁在执行
> 模型不是自己真的去执行工具，它只是告诉应用我想调用哪个工具、参数是什么。真正执行的是后端系统。模型负责决策意图，应用负责权限控制和实际动作。

#### MCP 怎么讲最稳
> MCP 是 AI 应用连接外部工具和数据源的标准协议层，有点像给模型生态做统一接口。它的价值不是多了一个新名词，而是让工具接入从硬编码逐渐走向标准化。

### 8.3 Agent 与工作流

#### Workflow 和 Agent 的区别
> Workflow 更像预先设计好的步骤流程，系统来决定下一步；Agent 更像把部分运行时决策权交给模型。二者最大的区别不是复杂度，而是谁掌握决策权。

#### 为什么很多场景不用 Agent
> 很多业务流程本来就是固定的，比如审批、抽取、审校、生成固定格式内容，这些用 Workflow 更稳、更便宜、更容易测。

#### Prompt Chaining 有什么价值
> 它把大任务拆成小任务，一步一步做，比把所有要求一次塞进一个超长 prompt 更可控。不仅效果更稳，也更容易排查是哪一步有问题。

#### Agent 最怕什么
> 最怕两件事：一是没有边界，工具开得太多；二是没有终止条件，导致循环调用、成本失控。做 Agent 我一定会关心工具白名单、步数上限、预算上限和异常恢复策略。

### 8.4 评估、安全与运维

#### 为什么 AI 应用一定要做评估
> 模型输出不是稳定确定的，同样的问题不同版本、不同参数、不同 prompt 下结果都可能变化。没有评估，你根本不知道一次优化是真的优化，还是只是换了一种说法。

#### 评估通常看哪些指标
> 分三层。第一层效果：任务成功率、结构化输出正确率、工具调用成功率。第二层工程指标：延迟、token 消耗、失败率。第三层业务指标：人工复核通过率和用户满意度。

#### Prompt Injection 怎么理解
> 用户通过输入诱导模型忽略系统规则、泄露信息或者执行不该执行的动作。提示词隔离只能降低风险，不能把它当绝对安全边界。真正稳的做法还是权限、审计、输出校验和人工兜底一起上。

#### 为什么工具权限很关键
> 工具一旦带副作用——发邮件、建工单、改数据、触发流程——风险就很大。模型只能提议调用，系统必须负责鉴权、白名单、幂等和审计。

#### AI 应用线上最该看什么监控
> 四类：首 token 延迟和总延迟、输入输出 token、工具调用成功率、失败和重试比例。不看这些指标很难定位问题。

#### 成本治理怎么做
> 我不会只看模型单价，而是看整条链路的总成本。模型路由、控制上下文长度、限制输出长度、缓存、压缩工具链、对高成本流程做配额和审批。

#### AI 应用怎么做灰度和回滚
> AI 应用回滚的不只是代码，还包括模型版本、prompt 版本、工具定义和路由规则。把这些都当成可版本化对象管理。上线时尽量先灰度。

### 8.5 结合项目的口语化答法

#### 如果面试官问你项目里最能体现 AI 工程化的点是什么
> 我会从三块讲。第一块是模型接入抽象，不同 Provider 的统一封装。第二块是 Workflow 节点执行，真实 AI 能力经常是流程里的一环。第三块是 Trigger 调度和异步执行，说明系统不是 demo，而是能自动化运行。

#### 如果面试官问这个项目除了 RAG 你还能讲什么
> 多模型 Provider、工作流引擎、节点执行、触发器、异步任务、容器化启动、模块化边界。就算不聊检索链路，这个项目本身也能支撑我去讲一套完整的 Java AI 应用工程化能力。

#### 如果面试官问你和只会调 OpenAI API 的人区别在哪
> 我不仅会调模型，还会考虑模型选型、Prompt 约束、结构化输出、工具边界、状态管理、并发治理、评估、安全、监控和上线策略。我更关注的是怎么把模型接成一个生产系统。

### 8.6 RAG 高频题口语答法

#### 什么是 RAG
> RAG 就是检索增强生成。先去外部知识库里找资料，再结合找到的资料让模型回答。主要解决两个问题：大模型知识有截止时间，企业私有知识原本就不在模型参数里。

#### 为什么企业更常先做 RAG，而不是先微调
> 大多数企业问题不是模型不会说，而是模型不知道企业自己的知识。制度文档、产品手册、项目资料，更适合通过外部知识检索接进来。微调更像调整模型行为和风格，RAG 更像给模型补知识。

#### 标准 RAG 链路怎么讲
> 分两段。离线阶段：文档解析、清洗、切分、Embedding、建索引。在线阶段：用户提问后做检索召回、融合或重排、组装 Prompt，再交给模型生成答案。

#### 为什么 Chunk 很重要
> Chunk 决定检索单位，也决定最终喂给模型的上下文粒度。切太小会丢上下文，切太大噪声又多。Chunk 本质上是在定义知识单元。

#### 为什么只做向量检索不够
> 向量检索更擅长语义相似，但对错误码、型号、缩写、专有名词这些精确匹配场景不够稳。所以一般会做向量检索加全文检索的混合检索。

#### 为什么需要 Rerank
> 第一阶段召回的目标是别漏掉，不是最终排序最优。Rerank 更像第二阶段精排，重新判断 query 和候选片段的相关性。

#### 多轮对话为什么更难做检索
> 用户后面几轮经常只说代词或省略句。直接拿去检索语义不完整，所以要做 query rewrite，把当前问题改写成独立完整问题。

#### 长上下文会不会替代 RAG
> 不会完全替代。小知识库可以直接塞，大知识库仍然需要 RAG。长上下文也有 lost in the middle 问题。更准确的说法是替代一部分简单场景，但不替代企业级 RAG。

#### 结合这个项目，RAG 部分你会怎么讲
> 三块。第一块知识入库：文档解析和切分策略，标题层级、表格保留。第二块检索抽象：统一入口支持向量、全文和混合检索。第三块工作流接入：把检索结果整理成后续模型节点可消费的上下文。

#### 如果问你这个项目的 RAG 还能怎么优化
> 按收益优先级排：先补离线评测集 → 加 query rewrite → 接专门的 rerank 模型 → 补检索链路埋点和引用展示 → 更前沿的 Self-RAG、GraphRAG 后面再评估。

#### RAG 系统设计题怎么收尾
> 我理解的 RAG，不是给模型塞几段文本，而是把企业知识工程化，变成可检索、可过滤、可追踪、可评估的回答能力。它真正难的地方不在生成，而在检索链路和知识治理。

## 九、纯问答清单（55 题快速背诵版）

### 大模型基础（18 题）

1. **什么是大语言模型**：基于上下文预测下一个 token 的概率模型，不是数据库。
2. **Transformer 为什么是核心架构**：自注意力机制 + 可并行扩展。
3. **token 为什么重要**：模型按 token 处理，成本、上下文、延迟都按 token 算。
4. **temperature、top_p、top_k 控制什么**：生成随机性，结构化任务 temperature 调低。
5. **什么是上下文窗口**：单次请求最多看到的 token 数，长不等于利用得好。
6. **什么是幻觉**：概率生成导致的不准确内容，用工具、校验、评估共同控制。
7. **开源 vs 闭源怎么选**：闭源综合强、稳定；开源可私有化、可控、可量化。
8. **云 vs 本地怎么选**：云适合快速上线，本地适合数据敏感和长期成本可控。
9. **预训练、SFT、RLHF、DPO 区别**：预训练给通用能力，SFT 调任务行为，RLHF/DPO 做对齐。
10. **为什么不先微调**：多数问题根源不在模型，在任务拆解和流程设计。
11. **LoRA 和量化区别**：LoRA 低成本微调，量化低成本推理。
12. **蒸馏是什么**：大模型教小模型，降低推理成本。
13. **TTFT 和 TPS**：首 token 时间和每秒 token 数，优化体验先盯 TTFT。
14. **KV Cache**：缓存历史 token 注意力计算结果，推理优化基础设施。
15. **为什么长上下文更贵更慢**：输入 token 多、注意力重、显存高。
16. **量化是什么**：用更低精度表示参数，效果换成本。
17. **llama.cpp / Ollama / vLLM / Xinference 区分**：底层推理/开箱即用/高吞吐服务/统一平台。
18. **多模态模型**：处理文本之外图像、音频、视频等输入输出。

### Java 工程与框架（16 题）

19. **Java 为什么适合 AI 应用**：企业后端工程成熟，系统集成、审计、调度、运维完善。
20. **Java 做 AI 短板**：训练和推理生态在 Python，常见模式 Java 编排 + Python 底层。
21. **Spring AI 定位**：把 AI 能力纳入 Spring 生态，可配置、可观测、可治理。
22. **LangChain4j 定位**：Java 友好的大模型应用框架，快速开发体验。
23. **Spring AI vs LangChain4j**：看团队是更看重 Spring 统一治理还是开发体验。
24. **什么时候用官方 SDK**：少量模型调用、需第一时间接入新能力时。
25. **为什么做 Provider 抽象**：长期不会绑死一个供应商，方便切换、灰度、路由。
26. **Prompt 为什么要工程化管理**：Prompt 是业务逻辑一部分，需版本管理和测试。
27. **结构化输出为什么重要**：业务系统最终消费字段，不是自由文本。
28. **为什么不能只靠"请返回 JSON"**：概率生成不保证格式一致，需 schema 和校验。
29. **多轮对话历史为什么不能无限追加**：token 成本、延迟、上下文污染持续增加。
30. **Chat Memory 解决什么**：多轮对话状态延续，但非无限记忆也非知识库。
31. **Tool Calling 完整链路**：模型提意图 → 应用解析执行 → 结果返回。
32. **工具定义最重要三样**：工具名、工具描述、参数 schema。
33. **参数 schema 为什么关键**：决定模型怎么构造参数，不清则乱猜。
34. **Tool Calling 和 MCP 关系**：TC 是调用机制，MCP 是标准协议层。

### RAG（10 题）

35. **RAG 四段流程**：知识准备 → 查询检索 → 上下文增强 → 生成回答。
36. **RAG vs 微调**：RAG 解"知识从哪来"，微调解"模型怎么说"。
37. **为什么 Chunk 是核心**：决定检索单位和上下文粒度，影响召回、精排、成本和生成。
38. **混合检索为什么重要**：向量语义泛化 + 全文精确命中，提高鲁棒性。
39. **为什么需要 Rerank**：第一阶段别漏，第二阶段精排到最优。
40. **Top-K 怎么设**：召回取 20-50，重排后取 3-8 给 LLM。
41. **metadata filter 重要性**：企业是从合法范围检索，不是从全宇宙检索。
42. **为什么多轮对话检索下降**：用户说代词的省略句，需 query rewrite。
43. **长上下文替代 RAG 吗**：小库可塞，大库仍需 RAG，有 lost in middle 问题。
44. **RAG 优化优先级**：评测集 → query rewrite → rerank → 埋点引用 → 前沿方案。

### Agent、评估、安全、运维（11 题）

45. **Workflow vs Agent**：Workflow 代码主导决策，Agent 模型主导决策。
46. **为什么很多场景不用 Agent**：流程固定时 Workflow 更稳、更便宜、更易测。
47. **Agent 终止条件为什么重要**：防止循环调用、成本失控。
48. **为什么 AI 应用必须做评估**：输出不确性，需判断每次变动是进步还是退步。
49. **离线 vs 在线评估**：离线做版本回归，在线看真实业务表现。
50. **Prompt Injection 怎么防**：权限边界 + 工具白名单 + 输出校验 + 脱敏 + 审计。
51. **为什么需要 Tracing**：一次响应的模型调用、工具调用、缓存、重试链需要全链路追踪。
52. **成本治理怎么做**：模型路由、上下文压缩、缓存、缩短工具链、配额审批。
53. **为什么灰度发布**：模型/prompt/工具变化都可能行为漂移。
54. **回滚什么**：模型版本、Prompt 版本、路由规则、工具定义、Agent 策略。
55. **AI 服务扩容为什么不能只加 Pod**：瓶颈可能在模型服务本身、GPU、外部工具。

## 十、模拟面试题（初/中/高级）

### 10.1 初级模拟题

> 每题控制在 1-2 分钟。如果答不满 30 秒，说明这一块准备还不够。

#### 1. 介绍一下你理解的 Java AI 应用开发是什么
**要点：** 不是训练模型，是把模型能力接入业务系统。重点在模型接入、Prompt、结构化输出、工具、工作流和运维治理。Java 价值在企业系统集成和工程化落地。

#### 2. 什么是大语言模型
**要点：** 基于上下文预测下一个 token；具备通用生成和理解能力；不是数据库，不保证天然事实正确。

#### 3. Transformer 为什么重要
**要点：** 自注意力机制；适合并行训练；支撑模型规模扩展。

#### 4. token 为什么比字数更重要
**要点：** 模型按 token 处理；成本、上下文、延迟都与 token 强相关；中文、英文、代码 token 化效率不同。

#### 5. temperature 是干什么的
**要点：** 控制随机性；越高越发散，越低越稳定；结构化任务一般调低。

#### 6. 什么是幻觉
**要点：** 看似合理但不真实；根因是概率生成；需要用工具、校验和评估来控制。

#### 7. 为什么 Java 也能做 AI 应用
**要点：** AI 应用落地本质是后端工程问题；Java 在系统集成、审计、调度、监控方面成熟；训练和应用是两层问题。

#### 8. Spring AI 和 LangChain4j 你怎么理解
**要点：** Spring AI 偏 Spring 生态治理；LangChain4j 偏 Java 开发体验；选型看团队体系。

#### 9. 什么是结构化输出，为什么重要
**要点：** 让模型输出 JSON 或确定字段；便于 Java 对象映射和业务落库；比纯文本解析稳定。

#### 10. Tool Calling 是什么
**要点：** 模型提出调用意图；应用实际执行工具；模型不直接拥有系统权限。

#### 11. Workflow 和 Agent 有什么区别
**要点：** Workflow 是固定流程；Agent 是动态决策；按业务需求选，不是按复杂度选。

#### 12. RAG 是什么
**要点：** 检索增强生成；先去知识库检索相关内容；再让模型基于检索结果回答。

### 10.2 中级模拟题

> 每题控制在 2-3 分钟。考察是否能讲清楚原理和取舍。

#### 1. 你们项目里的模型接入是怎么做的

**参考要点：**
- 统一 Provider 接口抽象，不直接依赖任何一家 SDK。
- 多模型路由：简单问题走便宜模型，复杂问题走强模型。
- 熔断、限流、降级一样不少，把模型当不可靠外部资源对待。
- 结合 maxkb4j 项目：`IModelProviderService` 统一抽象 ChatModel / EmbeddingModel / ScoringModel。

#### 2. 结构化输出你们是怎么落地的

**参考要点：**
- 先利用 JSON Schema 或框架的 Structured Output 能力做硬约束。
- Java 层定义 DTO，由框架自动映射。
- 失败时做重试，重试再失败就走降级兜底。

#### 3. Prompt 你们怎么管理和测试

**参考要点：**
- Prompt 模板化，变量替换，配置化管理（Nacos/Apollo/数据库）。
- 版本管理和回滚。
- 回归测试：Prompt 改动前后在固定评测集上对比效果。

#### 4. 多轮对话的上下文你们怎么控制

**参考要点：**
- 不无限追加历史，按窗口、摘要和关键状态管理。
- Token 预算策略。
- 会话 ID 贯穿全链路。

#### 5. Tool Calling 的安全边界你们怎么设计的

**参考要点：**
- 工具按场景分层开放，不是全部暴露。
- 只读工具和写工具权限分级。
- 高危操作二次确认或人工审批。
- 有审计记录。

#### 6. 你们怎么做 RAG 的效果评估

**参考要点：**
- 不能只看主观感受。
- 构建 Golden Dataset，包含问题、标准答案、标准引用文档。
- 用 RAGAS 指标：Context Relevance、Faithfulness、Answer Relevance。
- 每次改 Prompt 或切分策略跑全量评估。

#### 7. 你们在文档切分上有什么实际经验

**参考要点：**
- 不是简单按长度切。
- 先按标题层级递归切分保留结构。
- 表格做专门保护。
- 超长段落按句子二次切分。

#### 8. 混合检索你们具体怎么做的

**参考要点：**
- 向量检索负责语义泛化。
- 全文检索负责关键词精确命中。
- 用 RRF（Reciprocal Rank Fusion）或加权求和做融合。
- Java 里用 CompletableFuture 并发检索再内存融合。

### 10.3 高级模拟题

> 每题控制在 3-5 分钟。考察架构思维、成本意识、风险判断和系统设计能力。

#### 1. 如果让你从零设计一个企业级 AI 助手平台，你会怎么分层

**参考要点：**
1. 模型接入层：多 Provider 统一抽象、路由、限流、缓存。
2. 会话与编排层：多轮上下文管理、Workflow/Agent 编排。
3. 检索与知识层：RAG 全链路，含知识库管理。
4. 工具与集成层：工具注册、权限管控、MCP 协议。
5. 评估与观测层：离线评估、在线监控、Tracing。
6. 运维与治理层：灰度、回滚、审计、多租户、成本管控。

#### 2. 如果要支持多租户，AI 应用有哪些特殊点

**参考要点：**
- 知识库、Prompt、模型配额、工具权限都要隔离。
- 检索阶段必须做 metadata filter。
- 会话缓存和上下文不能跨租户串线。
- 成本按租户核算。
- 审计日志需要区分租户。

#### 3. 如果大模型 API 突然不可用，系统怎么保证基本可用

**参考要点：**
- 多模型 Fallback：主模型不可用自动切换备选。
- 语义缓存：高频问题直接返回缓存答案。
- 前端降级：展示检索到的原始文档片段。
- 降级策略不是"出了问题再想"，而是上线前就设计好。

#### 4. 你如何说服团队不要在项目中滥用 Agent，而优先用 Workflow

**参考要点：**
- 从成本、可测性、可审计性、稳定性四个维度对比。
- Agent 链路更长、延迟更高、更难评测、更难审计。
- 业务流程固定时 Workflow 足够。
- 举出实际案例说明。

#### 5. 如果让你优化一个已经上线的 RAG 系统，你会怎么排优先级

**参考要点：**
1. 先补离线评测集（没有评测无法判断改进方向）。
2. 再加 query rewrite（提升多轮对话检索质量）。
3. 再引入 rerank（提升最终送给 LLM 的上下文质量）。
4. 再补全链路埋点（Tracing、Token 统计、延迟监控）。
5. 最后考虑 Self-RAG、GraphRAG 等前沿方案。

#### 6. 你觉得 AI 应用里最难的不是技术问题，而是什么问题

**参考要点：**
- 效果和成本之间如何持续平衡。
- 如何让业务团队理解模型能力边界和局限性。
- 如何建立有效的评估和反馈闭环。
- 如何在安全和体验之间找到平衡点。
- 本质上AI应用最难的是"工程治理"——把不确定的模型输出变成可预期的系统行为。

#### 7. 如果面试官最后让你总结你对 Java AI 应用的理解

**参考话术：**
> 我理解的 Java AI 应用，不是单点模型调用，而是用 Java 企业级工程能力把模型、工具、业务系统和治理体系整合成一个稳定、可评估、可演进的生产能力。模型决定能力上限，工程治理决定交付下限。

## 十一、不会回答时的应急模板

> 面试中一定会遇到你不会的问题。面试官评分的 30% 看你会不会"不会装会"。以下是经过验证的应对策略。

### 11.1 三步应对法

**第一步：坦然承认边界（不要编）**

> "这个问题我目前的理解有限，还没有亲自做过这一块。"

❌ 错误示范："这个我做过，就是……"（然后开始编——面试官一旦追问就穿帮）  
✅ 正确示范：先承认，再展示你有相关的知识基础。

**第二步：关联已有经验（展示迁移能力）**

> "不过我做过类似的 X，核心区别在于……如果让我来做 Y，我理解的关键挑战是……"

这展示了你的学习能力和知识迁移能力，面试官对"不会但能快速上手"的候选人评价远高于"不会装会"的。

**第三步：给出思路和优先级（展示工程思维）**

> "如果让我来设计这个方案，我会优先考虑 A、B、C 三个点，其中 A 是核心、B 是兜底、C 是锦上添花。我会先花 X 天把 A 跑通验证效果，再决定是否投入 B 和 C。"

这展示了你的系统设计能力和 trade-off 判断力。

### 11.2 常见追问的化解话术

**Q：你有没有做过多智能体系统？**

> "我目前主要做单 Agent + Workflow 编排，还没有上过多智能体。但我理解多智能体的核心挑战在于角色边界划分、状态同步和终止条件控制。如果让我来设计，我会先确认任务是否真的需要多角色协作——很多时候单 Agent + Prompt Chaining 就够了。如果确实需要，我会用 Orchestrator-Workers 模式，一个编排者负责拆分和聚合，多个 Worker 各司其职，同时严格控制步数和预算上限。"

**Q：你们有没有做过 Embedding 微调？**

> "目前我们用 BGE-M3 的通用版本，配合 Query Rewrite 和同义词映射，效果已经能满足业务需求。我了解 Embedding 微调的基本思路——用对比学习，收集 (query, positive_doc, negative_doc) 三元组做训练。如果未来效果不够，我会先收集几百条业务标注数据，用 FlagEmbedding 做微调，然后通过 Xinference 暴露给 Java 侧调用。"

**Q：你怎么看你们系统的架构缺陷？**

> "坦率说，我们目前的架构有几个可以改进的地方。第一是缓存层——目前只做了 Redis 会话缓存，没有做语义缓存，高频重复问题还在反复调 LLM。第二是监控——我们只监控了接口级别的 QPS/RT，没有做到 Span 级别的 Trace，排查问题时需要翻多个系统的日志。第三是 Prompt 版本管理——目前还是 Git 管理，变更需要走发布流程。如果给我时间，我会按优先级逐个补上。"

### 11.3 万能兜底句式

当实在没有任何相关知识时，最后一张牌：

> "这个问题确实在我的知识边界之外。不过我对这类问题很感兴趣，面试结束后我会马上去了解一下。能请您简单介绍一下你们团队在这一块是怎么做的吗？"

这句话同时做到了：诚实 + 好学 + 把话题抛回给面试官（人都有表达欲，让面试官讲自己的经验能缓解冷场）。
